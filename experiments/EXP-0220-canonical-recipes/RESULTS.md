## 1. What "no donor" cost, and why it is not the same claim EXP-0167 made

EXP-0167 also reported zero-copied programs, and EXP-0173 scored `falu2` and `device_store`
`generated-no-donor` off that corpus. Two things are different here.

1. **`base_slot` is no longer read off a compiled instruction.** EXP-0167 re-derived it by
   disassembling its own carrier and tagged it `CARRIER` — honest, and still a required
   instruction field taken from a compiler-emitted instruction. **Arm S0 measures it
   instead**: sweep `base_slot` in a generated store and observe which bound buffer the
   write lands in. Result, identical in both runs:
   `slot 0 → out, slot 1 → mem, slot 2 → imem, slots 3..7 write none of the three and fault
   none`. The field is now `RULE` with a hardware citation, and the `CARRIER` count is 0.
2. **The oracle is the complete state, not the destination.** Every case dumps r0..r23 to 24
   distinct out words through a fixed read-back plan that never co-varies with the field
   under test, and all three bound buffers are read back and compared **byte for byte**
   against a host prediction computed before the GPU was touched. A store that lands in the
   wrong buffer, an aliased extra register write, or a write one byte wide instead of four is
   caught, not missed.

## 3. The seven corrections this experiment forced on documented rules

All seven were found by the disclosed pre-freeze pilot (`work/pilot/p01..p08`,
`harness/diag220.py`), folded into `PRE_REGISTRATION.md` §6 **before** the contract was
frozen, and then re-measured inside the frozen matrix.

**C1. `falu2.opflags` bit1 is OPERAND-CLASS DEPENDENT.** With a GPR `srcB` it is the
documented release-src1 lifetime bit — the register reads 0 afterwards, seen directly through
a re-read instruction rather than inferred. With a **non-GPR / inline-immediate `srcB` it
NEGATES the immediate**, XORing with `srcB_neg`. The discriminating control is one program,
four instructions differing only in those two bits, srcA a loaded 10.25 and |imm| 4.0:

| opflags bit1 | srcB_neg | result | effective sign |
|---|---|---|---|
| 0 | 0 | 14.25 | +4.0 |
| 0 | 1 | 6.25 | −4.0 |
| 1 | 0 | 6.25 | −4.0 |
| 1 | 1 | 14.25 | +4.0 |

with the paired GPR control showing no sign effect at all. This **explains** EXP-0167's
committed `INLINE_NEG0_SIGN = -1`: that generator always set bit1, so the constant absorbed
it. It also **supersedes** EXP-0090 finding_1's reading of bit1 as "both real". In the frozen
matrix: `opflags` 32/32, the inline codec 256/256, the operand-class matrix 32/32.

**C2. `falu2.mod_hi` bit0 set means the destination is NOT WRITTEN AT ALL** — not a wrong
value, not a silent zero: the register keeps its previous codeword against a poisoned
buffer. Bits 2 and 3 are an **accept/forward control for a `device_load` result still in
flight**: with the load immediately preceding, only `0xC` of {0,4,8,C,E} delivers the operand;
with **one** intervening instruction all five do. `mod_hi = 0xC` is correct in every context
tested and is the canonical emitter value. This supersedes EXP-0167's ALU/LOAD split, which
was measured only load-adjacent — the controlling variable is the in-flight load, not srcA's
provenance. Frozen matrix: `mod_hi` 32/32 across two provenance classes, and the dedicated
4 provenance × 5 values × 3 distances arm **60/60**.

**C3. `device_store.addr_mode` bit1 is the store-side twin of `mod_hi` bits 2/3.** With the
store's data register holding a live load result: bit1 set forwards it; **bit1 clear stores
the STALE register value and DROPS the load** — the destination register never receives it.
With ALU-computed data the field is inert over all 256 values. **512 of 512 gated cases
exact.** This refines EXP-0141's "the other 128 store 0": they store the stale register, and
the load is lost.

**C4. A `device_store` RELEASES its index register.** After the store the register reads 0,
and a **second store reusing it addresses with index 0**. Both predicted in advance and
matched.

**C5. A `device_store` whose index register was written by the immediately preceding
`device_load` addresses with the STALE value**; one intervening instruction fixes it. This is
the same in-flight rule as C2/C3 seen on a third path, and it is a trap for an emitter: the
store looks correct and silently writes to the wrong address.

**C6. `device_store.extmode` bit0 is NOT a don't-care.** Only the even values 0..126 deliver
register r(extmode/2) — 64 of 64 exact, each register carrying a unique codeword. All 126 odd
values were dispatched and none is exact. 252..255 fault. 128..250 are recorded, not modelled.

**C7. `mov_imm` immediates that do not tokenize as a 2-byte instruction are nine, not one.**
EXP-0140 records `imm7 == 12`; measured offline against the pinned length rule the set is
`{6, 12, 22, 38, 54, 70, 86, 102, 118}` — 12 plus every `imm7 ≡ 6 (mod 16)`. A build-time
gate refuses any case whose generated offsets are not walk boundaries.

## 4. Other results

* **`st_format`'s multi-element source rule is confirmed.** All six documented shapes
  (32/16/8-bit scalar and 2/3/4 × 32-bit vector) were predicted **byte-exactly** before the
  run and matched: element *n* comes from register `extmode/2 + n`, and a 2-byte or 1-byte
  store leaves the rest of the word still poison.
* **b16 operands** read the low half of the register and write a full binary32 result: 32/32
  exact — but only once the operands were changed to **packed-half codewords**. With the
  ordinary `(j+1)/4` codewords the low half is all zero, both operands read 0.0, and the arm
  passes *by construction*. That is §5a's detection-power pitfall, caught in the pilot.
* **`falu2.opsel` 0, 1, 2, 3 and 7 FAULT** the command buffer in the 6-byte form,
  reproducibly in both runs; 6 executes and writes the destination. Only 4 (`fadd`) and
  5 (`fmul`) are usable.
* **Denormal results flush to zero**: `fmul(smallest denormal, 19.5)` gives exactly 0, where a
  host double predicts a denormal.
* **Two descriptor ambiguities**, recorded rather than fixed (the orchestrator owns
  `db.json`): `falu2` with `opsel` 0/1 assembles to bytes that also satisfy `falu_compact4`;
  `device_store` with `space` 6/22 also satisfies `frag_color_store`/`imageblock_store`, and
  the length-rule walk then desynchronises for the remaining 16 stores in the program. Both
  `space` values fault on hardware.
* **Threadgroup-space stores (`space` bit1) fault** against a device-bound buffer — 4 of 4,
  both runs. This is the gap that keeps `device_store` at `generated-no-donor`.

## 5. Exactly what the canonical `falu2` recipe covers, and what it does not

Covered, each with a host prediction of the complete state:

| axis | coverage (exact numerator/denominator) |
|---|---|
| `dst` | 16 / 16 dense, including r15 with a rescue that restores the index register |
| `srcA_reg` | 64 / 64 dense, each register carrying a unique codeword |
| `srcB_reg` (GPR) | 64 / 64 dense |
| `srcB` inline float immediate | 64 / 64 codes × 2 signs × 2 ops = 256 / 256 exact |
| `srcB` constant zero | classes 2 and 3, both signs |
| `opflags` | 32 / 32 dense, with a per-source re-read truth table |
| `mod_hi` | 16 / 16 dense in two operand-provenance classes |
| `ctrl` | 32 / 128 — bits 0/1 are the instruction-length selector, held at the 6-byte form |
| `opsel` | 8 / 8 dispatched; 2 usable, 5 fault, 1 recorded |
| operand size | b32 and b16, 32 / 32 |
| `srcA_reg_top`, `srcB_reg_top` | 2 / 2 each |
| operand provenance | live load / ALU / `mov_imm`, at instruction distances 0, 1, 2 — 60 / 60 |
| IEEE boundary operands | ±0, ±1, ±2, ±0.5, smallest normal, FLT_MAX, 2²⁴ — 18 gated exact |

**Not covered, stated plainly:**

* **the uniform-register operand source** (`srcB_class = 1` with index 0..63). Eight cases
  were dispatched and are recorded, but this carrier does not seed the uniform file so they
  are not predicted. I did **not** treat this as a blocker, because every value a uniform
  could supply is reachable through a GPR or the inline immediate — both fully proven here —
  so an implementer can generate any `falu2` they need without it. It stays **open on the
  capability map**, and a reader who disagrees with that judgement should read the verdict as
  `generated-no-donor` with one gap.
* `opsel` 6; NaN payloads, infinities and denormals (recorded, not claimed).

## 6. Why `device_store` is NOT canonical

`device_store` passed everything `falu2` passed — 819 gated cases, 0 failures, the full
256-value `addr_mode` sweep in both data-source classes, all six `st_format` shapes, a
hardware-probed `base_slot`. It is held back by **one class a compiler routinely selects and
this recipe cannot emit: the threadgroup address space.** No threadgroup carrier was built,
and the four `space` bit1 values fault against a device buffer. Two smaller items stay open:
`extmode ≥ 128` (a data-register index ≥ 64) is recorded but unresolved, and nine of its
fields were **sampled** (10, 37, 8, 7, 8, 5, 5, 6 and 7 values) rather than swept densely as
§3 asks for a `w ≤ 8` field. Those nine already carry `hardware-run` labels from EXP-0141 and
EXP-0169's dense sweeps, so this is a coverage statement about *this recipe*, not a doubt
about the fields.

## 7. How this method could have called a recipe canonical while a field was still
donor-supplied

Three ways, and each is closed by a specific artifact rather than by intention:

1. **By trusting the provenance tag instead of the bytes.** `synth220.FV` requires a
   provenance class on every field, but a tag is just a string an author types. What makes it
   evidence is that `analysis/census220.py` **rebuilds every program from the authored inputs
   and asserts its sha256 against raw** (0 mismatches over 1,584 cases) before counting the
   tags — so the census describes the bytes that executed, not a re-derivation.
2. **By reading a required field off our own compiled carrier and calling it "not a donor".**
   This is exactly what EXP-0167 did with `base_slot`, in good faith, with the class named
   `CARRIER` so it was visible. EXP-0220's answer was to *measure* the field instead (arm S0)
   and then require `CARRIER == 0`, not merely to report it.
3. **By letting the oracle absorb the unknown.** The pilot shows this concretely: at first
   every "corrupt" case was emitted with `predict=False`, so a corruptor that silently
   delivered the correct answer would have been scored `unpredicted` and quietly excused. The
   frozen matrix predicts the **truthful** value for corrupt cases too, so the `corrupt`
   bucket is falsifiable. The same pitfall in its other direction is the b16 arm, which
   passed 8/8 *by construction* until the operands were changed so the low half was non-zero.

The one that actually bit me is smaller and is on the record: I froze
`predicted_bucket: exact` for seven `index_reg` values already documented as faulting, so my
own Gate C shows 7 failures that are really a contract error. I left them failing.

§2 is explicit that field labels alone are not an emittability proof. If the dashboard is
meant to keep reading a field-label count, these two rows want re-deriving rather than
inheriting.

## 10. Limitations

* Single-thread dispatch (grid 1, threadgroup 1). Nothing here says anything about
  cross-lane or cross-thread behaviour.
* One carrier shape. The lifetime rules C2–C5 were each seen on two or three independent
  paths within it, but not in a structurally different carrier (fragment, or a threadgroup
  kernel).
* The `mod_hi` bits-2/3 map is **partial**: which subset a single set bit accepts depends on
  how many loads are in flight, and that dependence is not resolved.
* 39 device resets, all self-inflicted and all recovered. A run on a busy machine would have
  made 20 of them look like a neighbour's problem; this one was measured quiet.
