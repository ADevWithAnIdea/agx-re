## Item 1 -- exact branch-reach fault/silent-zero/correct boundary map

**Hypothesis (pre-registered before this experiment's own reconnaissance sweep, which
already ran and is disclosed above):** EXP-0104 found the encoding's nominal 48-bit
signed range is far narrower in practice, bracketed by 6 points (±8B fault/hang,
+4096B silent-OK-zero, ±0x400000B fault). The finite-resource mandate requires the
EXACT boundary. Two competing models going in: (A) a SINGLE sharp threshold per
direction (fault below/above some byte count, silent-zero beyond it) that bisection
can pin to one exact byte; (B) an IRREGULAR/data-dependent region (since bytes beyond
the function's own extent belong to whatever else the compiler/runtime allocated
nearby, not to a clean "safe padding" zone) where fault and silent-zero interleave
unpredictably. Refuter for (A): any two adjacent byte offsets straddling the "found"
boundary that do NOT reproduce a clean single flip when re-tested. Refuter for (B):
a fully monotonic, single-flip sweep at fine granularity.

**Reconnaissance result (disclosed, `work/pilot/bisect_reach.py`, real M4 dispatches):**
model (B) is what was observed. Forward: `reach_baseline` (offset -44, target = the
loop head) is the UNIQUE correct point -- `delta=+1` already faults (zero slack).
Forward deltas +1..+32 are FAULT except one isolated HANG at +10. A dense 128-byte-step
sweep from +128 to +4096 shows a genuine CHECKERBOARD of FAULT and silent-OK-zero (not
a single threshold): solid FAULT from +128 to +896, then an interleaved mix from
+992 through +4096 (e.g. +1024/+1536/+2048 OK, +2560/+3072 FAULT, +3328..+4000 OK,
+4032 FAULT, +4048..+4094 OK, +4095 FAULT (odd byte), +4096 OK). Sparse far points
(+8192 FAULT, +16384 OK, +32768 through +4194304 all FAULT) show the checkerboard
resolves back to solid FAULT by ~+32768. Backward is qualitatively DIFFERENT: -1..-32
is FAULT/HANG only (one exception, delta=-2, which is OK/correct -- landing 2 bytes
before the documented target still executes correctly, a genuine alias hole), and the
dense 128-step sweep from -128 to -4096 is **uniformly FAULT/HANG, zero silent-OK-zero
points observed** -- backward never silently succeeds in the swept range.

**Frozen matrix (`harness/matrix.py: gen_reach_cases`):** re-runs this exact
reconnaissance as the formal, gated, two-capture-run experiment: `reach_baseline`
(unspliced control) + a fine ±1..32-byte sweep (64 cases) + a dense 128-byte-step
sweep out to ±4096 (64 cases) + 7 extra-fine points in the forward 896-1024 detail
zone + 12 far geometric points per direction out to ±0x400000 + the true 48-bit-field
extremes (+0x7FFFFFFFFFFF / -0x800000000000). 162 cases total, kind `locate_splice`
/ `reach_jump_offset` (`harness/run.py`): tokenizes the compiled `reach_loop`, finds
the real `jump` (not `jump_cond`) instruction, reads its natural 48-bit LE signed
offset field, and splices `baseline_offset + delta`. Every splice is an
INDEPENDENTLY CONSTRUCTED encoding (not a value the compiler ever emits), the
strongest CODEX evidence tier. **Coverage: COVERED.**

**Falsifier:** a run02 gated record disagreeing with run01 at any of the 162 cases
(the cross-run gate) would show the checkerboard is not deterministic given fixed
hardware+bytes -- itself a first-class, highly newsworthy result if it happened.

## Item 2 -- exact CF-03 nesting ceiling (push until it actually breaks)

**Hypothesis:** EXP-0104 reported LOWER BOUNDS (≥128 if-chain, ≥64 loop-nest, ≥12
divergent-nested-loop) with no failure observed. Genuine lexical nesting (N
simultaneously-live `if_push`/`pop_reconverge` frames) requires N levels of C-brace
nesting in MSL source; going deeper risks EITHER a hardware mask-stack-depth fault OR
a compiler/toolchain front-end limit, whichever is smaller. Refuter for "no compiler
limit": successful compilation at depth >1000. Refuter for "no HW limit within the
reachable range": a wrong/faulting/hanging result at any depth that compiled
successfully.

**Reconnaissance result (disclosed, `work/pilot/bisect_bracket.py`, real M4 compiles):**
Metal's Clang-based MSL front end enforces a fixed bracket-nesting ceiling
(`-fbracket-depth=256` diagnostic default, NOT adjustable through the public
`MTLCompileOptions` API `shdump.m` exposes -- confirmed by reading Apple's *public*
`MTLCompileOptions` header via the Xcode SDK, which offers only `fastMathEnabled`/
`languageVersion`/preprocessor macros, no bracket-depth escape hatch) that is reached
by lexical if/for nesting FAR before any depth EXP-0104 or this experiment observed a
hardware fault. Bisection against this experiment's OWN generator
(`harness/gen_deep_kernels.py`) found EXACT toolchain ceilings:
`ifnest2` (one `{` per `if` level): max compilable depth **254**, first
`COMPILE_FAIL` at **255**. `loopnest1b` (one `{` per `for` level): max compilable
depth **255**, first `COMPILE_FAIL` at **256**. `loopnestD2` (this experiment's new
linear-work divergent design, same brace shape as `loopnest1b`): independently
verified to share the identical boundary pair (255 ok / 256 fail). All three
max-compilable depths were ALSO dispatched on real hardware during reconnaissance and
matched their host oracle exactly (extending the HW-VALIDATED range from
128/64/12 to 254/255/255).

**`loopnestD2` design (new, replaces EXP-0104's `loopnestD` for the deep sweep):**
EXP-0104's original `loopnestD` used a genuinely divergent per-lane trip count in
{1,2,3} at EVERY level, multiplicatively -- total work grows as up to 3^depth, making
depths beyond ~12-16 dominated by execution TIME, not nesting depth, and risking a
GPU-timeout being misread as a "nesting ceiling". `loopnestD2` keeps genuine per-lane,
per-LEVEL divergence (trip count at level j = `1 + bit((j-1) mod 32) of v`, so
different lanes take different paths at every level) while keeping total per-thread
work LINEAR in depth (`depth` to `2*depth` inner-loop visits), decoupling "structural
nesting depth" from "total execution time" -- letting the sweep reach the SAME ~255
toolchain ceiling as the other two families without a runtime blow-up confound.

**Frozen matrix (`harness/matrix.py: gen_deep_cases`):** re-derives all of the above
as the formal capture: `ifnest2` at depths [128,192,224,240,248,252,254,255],
`loopnest1b` at [64,160,208,232,244,250,253,255,256], `loopnestD2` at
[12,64,128,192,224,240,252,254,255,256] -- 27 cases, kind `compile_limit`
(`harness/run.py`): attempts to compile via `shdump` only; a `COMPILE_FAIL` at the
known boundary depth is the EXPECTED result and is recorded as such (gated field =
deterministic Clang diagnostic tail), not hidden as an error; every depth that
compiles is ALSO dispatched and oracle-checked. **Coverage: COVERED**, with the
explicit, honest interpretation that the observed ceiling is TOOLCHAIN-imposed
(Clang's bracket-depth default), not a confirmed AGX hardware limit -- the true HW
ceiling for this specific reconvergence-stack resource remains UNKNOWN beyond the
toolchain-reachable range, and this is reported as such, not glossed over. This
matters for the driver: an NIR-based backend that does not go through Clang's C-like
parser (as a Mesa/asahi compiler would not) is not bound by this specific limit, so
the true HW ceiling is still an open question for that implementation path.

## Item 3 -- the dst_pred=1 mechanism

**Hypothesis:** `tools/agx-isa/db.json` independently documents a SEPARATE 4-byte
opcode variant, `if_push_pred` (byte0 `0x0f`, byte+1 low nibble `0x5` with a NONZERO
high nibble = a `pred` field, 4 bits), distinct from the plain `if_push` EXP-0104's
compiler always emits (high nibble always 0). This is a plausible mechanism: if
`icmp_pred`'s `dst_pred` really addresses a small predicate-register file, the
CONSUMER (`if_push`) would need to be encoded as `if_push_pred` with a MATCHING
`pred` value to correctly read that slot -- and EXP-0104 only ever spliced
`icmp_pred`'s `dst_pred` while leaving the consumer as plain `if_push` (implicitly
"slot 0"), which is not a fair test of model (A) from EXP-0104's own
`PRE_REGISTRATION.md`. Refuter for "if_push_pred selects the matching slot": a
MATCHED (dst_pred=N, if_push_pred.pred=N) pair produces CORRECT output for N>0 while
an unmatched pair does not. Refuter for "if_push_pred's pred field is inert": pred
value has NO effect on output for ANY dst_pred value, matched or not.

**Reconnaissance result (disclosed, `work/pilot/`, real M4 splice dispatches against
this experiment's own `kernels/cf_pred.metal`-equivalent pilot source):** a full
0-15 sweep of `if_push_pred`'s `pred` nibble ALONE (icmp_pred.dst_pred left at the
natural 0) reproduces the exact CORRECT baseline for all 16 values -- fully inert. A
25-point (dst_pred, if_push_pred.pred) MATRIX (diagonal 0-15 matched pairs plus
off-diagonal cross-talk points) shows output depends ONLY on `dst_pred`; the
`if_push_pred.pred` field NEVER changes the result, matched or mismatched. This
DIRECTLY REFUTES the `if_push_pred`-as-matching-consumer hypothesis. A supplementary
full `dst_pred` census (0-15, if_push unchanged) found: `dst_pred=0` correct;
`dst_pred=1` a UNIQUE, distinct corruption signature; `dst_pred=2` through `0xf`
(14 values) ALL collapse to the SAME second, uniform corruption signature ("every
lane takes the outermost else"). This exhaustively characterizes the field (prior
EXP-0104 evidence covered only {0,1,5,0xf}).

**Frozen matrix (`harness/matrix.py: gen_pred_cases`):** re-derives the above as the
formal capture: the same 25-point (dst_pred, if_push_pred.pred) matrix, kind
`locate_splice` / `predtest_dstpred_ifpush` (`harness/run.py`): tokenizes
`cf_pred.metal:predtest_004`, locates the FIRST `icmp_pred` and the immediately
following `if_push` (asserted adjacent by low-nibble pattern match), and splices BOTH
bytes independently per case -- an independently constructed TWO-FIELD encoding,
downstream-read (not the spliced instructions' own result). **Coverage: COVERED.**

**Driver-relevant conclusion this pre-registers as the expected write-up (subject to
the formal capture confirming it): there is no independently addressable predicate
register file reachable through this instruction pair; `if_push`'s "pred"-selecting
high nibble (as currently described in `db.json`) does not functionally select
which predicate `if_push` consumes, at least not for this consumer/producer pairing;
`dst_pred` must always be emitted as 0.** This is flagged to the orchestrator as a
candidate `db.json` documentation correction (this experiment does not edit
`tools/agx-isa/db.json` itself, per the "tools/* READ-ONLY" dispatch constraint).

## Item 4 -- static/immediate-index shuffle out-of-range

**Hypothesis:** EXP-0104 tested only the DYNAMIC (runtime-register-indexed) shuffle
form. A literal (compile-time-constant) index MIGHT compile to a qualitatively
different hardware encoding (an immediate embedded directly in the instruction,
matching EXP-0018's original "byte+6 = lane index/xor mask, encoded index<<1" note)
whose out-of-range behavior could differ from the dynamic form's documented
"idx & 0x1C" (simd_shuffle) / hard-zero (shuffle_xor, quad_shuffle) rules. Refuter:
identical failure signatures for static and dynamic forms at matched out-of-range
points would falsify "these are different mechanisms."

**Reconnaissance result (disclosed, `work/pilot/`, real M4 compiles+dispatches):**
a literal index DOES compile to a qualitatively simpler, single-instruction encoding
(`db.json`'s "dyn"-labeled mode enum values, e.g. `0x14`, turn out to appear for BOTH
literal and register-sourced indices depending on operand SHAPE, not literal-vs-dynamic
per se -- `db.json`'s "static"/"dyn" enum NAMES appear to be a pre-existing
mislabeling not corrected here; the operationally relevant distinction this
experiment establishes is INSTRUCTION COUNT: a literal index compiles to ONE
`simd_shuffle`-family instruction with the index embedded as `lane = index<<1`
(matching EXP-0018's original note), while EXP-0104's genuinely dynamic/register form
compiled (in this experiment's reconnaissance, on a fresh independent source) to a
qualitatively LARGER multi-instruction sequence -- confirming static and dynamic
really are different compiled shapes worth testing separately, whatever `db.json`'s
"mode" enum happens to be named). Critically: **the MSL compiler pre-MASKS an
illegal literal simd_shuffle index at compile time** (e.g. literal `40` compiles to
an embedded lane value equal to `(40 & 0x1F) << 1`, i.e. the hardware never sees the
raw out-of-range value through ordinary compilation) -- so testing the static form's
TRUE hardware behavior requires constructing the raw out-of-range immediate directly
via splice, exactly as this experiment's directive requires. Doing so (raw lane byte
spliced directly, bypassing the compiler's own masking) found: **`simd_shuffle`
static form gives HARD ZERO for any out-of-range index (raw=80, i.e. idx=40, unmasked)
-- DIFFERENT from the dynamic form's "&0x1C" aliasing (which would predict 8, not 0)
for the same effective index.** `quad_shuffle`'s static form (tested via a literal
that the compiler does NOT pre-mask, `quad_shuffle(v,(ushort)7)`, confirmed via a
natural compile+dispatch, `OWN-SHADER`/naturally-compiled -- the strongest possible
evidence for this specific point) ALSO gives hard zero, matching its dynamic form.

**Frozen matrix (`harness/matrix.py: gen_static_shuffle_cases`):** 32 raw-byte points
for `simd_shuffle` (4 in-range controls + 16 covering the dynamic form's tested
out-of-range region at finer resolution + 5 further + 3 extremes + 4 odd/hole
values), 13 for `simd_shuffle_xor`, 15 for `quad_shuffle` (60 cases total). Kind
`locate_splice` / `static_shuffle_lane` (`harness/run.py`): tokenizes each of
`shuf_static.metal`'s three single-instruction kernels, locates the sole
`simd_shuffle`-family instruction, and splices the raw `lane` byte (byte+6) directly
to an INDEPENDENTLY CONSTRUCTED value spanning the full legal-and-beyond range
-- bypassing the compiler's own literal-masking entirely, the strongest evidence
tier. **Coverage: COVERED**, including the odd-raw-value "hole" (raw values the
`index<<1` convention never produces naturally).

## Item 5 -- full vote family + the popcount 16->24 puzzle

**Hypothesis:** EXP-0104 found `simd_active_threads_mask()`'s low-16 raw bits
unchanged (still `0xFFFF`) after one fixed-pixel discard, but popcount jumped 16->24
(bits 16-23 differ), UNEXPLAINED. Competing candidate causes it left open: (a) a
scheduling/occupancy-padding artifact of discard changing register pressure/code
shape; (b) a genuine second set of helper/shadow lanes discard specifically
provisions. Refuter for (a) "generic to any divergent CF, not discard-specific": an
ordinary divergent RETURN (no discard) at the same fixed pixel ALSO shows the +8
jump. Refuter for "scales with discard count/varies with location": 2 discards give a
different popcount than 1, or discarding a different pixel gives a different jump.

**Reconnaissance result (disclosed, `work/pilot/`, real M4 4x4-target renders):**
an ordinary divergent RETURN (no `discard_fragment()`) at the identical fixed pixel
(0,0), otherwise structurally parallel to the discard kernel, shows **NO jump** --
surviving pixels report popcount 16, identical to the undiverged baseline. This
DECISIVELY REFUTES "generic to any divergent control flow" (return also uses real
branch/mask machinery per EXP-0104's CF-04 finding, yet does not trigger it) and
narrows the cause to something SPECIFIC to `discard_fragment()`. Two discards (at
(0,0) and (3,3)) give the SAME popcount as one discard (24, not e.g. 32) --
refuting "scales with discard count." A single discard at a DIFFERENT pixel (1,1)
instead of the corner (0,0) gives the SAME popcount (24) -- refuting
"location-dependent." Structural (compile-only) byte comparison shows the
discard/return kernels compile to genuinely different, LARGER instruction sequences
before the final vote-instruction read than the no-CF baseline, but this experiment's
current decode tables have undecoded residue in that exact fragment-stage sequence,
so the EXACT bit-level source of the extra 8 mask bits is not further isolated here
-- reported as a narrowed but still partially open finding, not a full resolution.

**Also reconnaissance-confirmed, extending SIMD-07 to the rest of the vote family:**
`simd_all(pred)` with `pred` FALSE only at the discarding pixel reads FALSE for every
surviving pixel after discard (the demoted lane's false predicate still counts --
INCLUDED, matching EXP-0104's `simd_active_threads_mask` finding). `simd_any(pred)`
with `pred` TRUE only at the discarding pixel reads TRUE for every surviving pixel
after discard (INCLUDED). Both are decisive, unambiguous (boolean-valued, no
lane-index-mapping needed), and reproduce the SAME conclusion via a genuinely
different vote instruction than EXP-0104 tested.

**Frozen matrix (`harness/matrix.py: gen_vote_cases`):** 13 fragment `render` cases
re-deriving all of the above formally: `f_mask_baseline_pc/_raw`, `f_mask_1discard_pc/_raw`,
`f_mask_1return_pc` (the decisive control), `f_mask_2discard_pc`, `f_mask_discard11_pc`,
`f_all_baseline/_1discard`, `f_any_baseline/_1discard`, and
`f_ballotpred_baseline_pc/_1discard_pc` (the EXPLICIT `simd_ballot(predicate)` form,
`db.json`'s pred=1 encoding, distinct from `simd_active_threads_mask`'s pred=0 form --
covering a 4th, previously-untested member of the vote family). **Coverage: COVERED**
for `simd_active_threads_mask`, `simd_all`, `simd_any`, `simd_ballot(predicate)`; the
exact bit-level mechanism of the popcount jump remains explicitly `UNKNOWN` (residue
undecoded), reported honestly rather than guessed.

## Item 7 -- SIMD-06 structural vs functional independence

**Hypothesis:** EXP-0104 found `simdgroup_barrier` compiles to byte-identical output
(0 added instructions) for every memory class in ONE tested shape (tg=32, natural
loop-exit reconvergence already present before the cross-lane read), and explicitly
flagged that this design cannot distinguish "genuinely a no-op" from "this test never
created a scenario where a barrier could matter." Refuter: ANY adversarial shape
(divergent per-lane call COUNT, divergent call PRESENCE, heavy register pressure,
double consecutive barriers, deep CF nesting) that causes the compiler to emit a
nonzero instruction for the barrier.

**Plan (no reconnaissance run for this item beyond the structural byte-length checks
already implicit in writing the kernels; the adversarial matrix below IS the first
test, run formally in both capture runs):** five paired (`_bar`/`_nobar`) adversarial
kernel shapes (`kernels/sgbar_adv.metal`) -- `sgbar_loop` (barrier inside a
per-lane-DIVERGENT-trip-count loop, so different lanes call the barrier a different
NUMBER of times), `sgbar_ifdiv` (barrier called by only SOME lanes -- divergent call
PRESENCE, a spec-questionable but hardware-observable shape), `sgbar_highreg` (heavy
register pressure around the barrier), `sgbar_double` (two consecutive barriers,
different memory classes), `sgbar_nested` (barrier at CF nesting depth 8). Each pair
gets a `structural_pair` (compile-only byte comparison, 0 GPU risk) case. The two
riskiest shapes (divergent call count / divergent call presence -- the ones a
strict SIMT-with-real-barrier-semantics machine could plausibly DEADLOCK on) ALSO get
a `compute` functional-correctness dispatch under a hard 10s timeout (a HANG here
would itself be the single most important finding of this item: proof the barrier is
NOT always a no-op).

**Frozen matrix (`harness/matrix.py: gen_sgbar_cases`):** 5 `structural_pair` cases +
2 `compute` (deadlock-risk, 10s hard timeout) cases = 7 total. **Coverage: COVERED**
for the adversarial shapes constructed; this does not claim to be an EXHAUSTIVE
search of the barrier's behavior space (an infinite space), only a targeted push at
the specific gap EXP-0104 flagged (does ANY reachable shape distinguish barrier
presence from absence, structurally or functionally).

## Confounders / limitations acknowledged up front

- **Compiler discretion**, as in EXP-0104: every kernel is compiled by Metal's own
  MSL->AGX compiler, not an independently-authored assembler for these families.
- **Item 1's branch-reach map is bounded by the SPECIFIC compiled `reach_loop`
  binary's memory layout** (a 146-byte `_agc.main` inside a specific archive); the
  exact checkerboard byte pattern beyond the function's own extent is almost
  certainly an artifact of THIS PARTICULAR compiled binary's surrounding bytes, not a
  general law -- reported as "the observed pattern for this compiled kernel", with
  the STRUCTURAL conclusion (no safe assumption is possible beyond the function's own
  extent; both fault and silent-corruption are live outcomes) generalized, not the
  exact byte offsets.
