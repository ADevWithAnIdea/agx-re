# RESULTS — EXP-0097 M4 varying/UVS export capacity + pre-raster special-output ABI

**Target: Apple M4 (G16G), local host, macOS 26.6.2 (25G82), Metal 4. M4-only; no A18 Pro claim
anywhere (A18 hands-off).** Two full official capture runs (`raw/m4_20260828_run01`,
`raw/m4_20260828_run02`), 140/140 cases each, **byte-identical across every gated field**
(`verify.py --captured m4_20260828_run01 m4_20260828_run02` → `cross_run_gate_pass: true,
issues_total: 0`); verdict counts 140 PASS / 0 FAIL / 0 TIMEOUT both runs. Zero faults, zero
`CMDBUF_ERROR`, zero hangs, zero host wedges across 280 total case executions.

Clean-room provenance: **OWN-SHADER.** Every MSL source is generated by
`harness/genkernels.py` (pure string templates, authored by us) and compiled through the public
Metal runtime (`newLibraryWithSource:` → `newRenderPipelineStateWithDescriptor:` → draw →
`getBytes:`). No Apple binary was introspected. No native AGX instruction was decoded or spliced
anywhere in this experiment (see §0 below on the db.json ALU-retention-flag caveat).
Inputs inspected: `harness/genkernels.py`-generated `.metal` sources (`work/gen/*.metal`,
regenerated identically by both runs) and the public `NSError`/pixel-readback text/values Metal's
own API returns to any caller.
Reproduction: `python3 harness/run.py --run <id> --out raw/<id>` (×2), then
`python3 harness/verify.py --captured <run_a> <run_b>`.
Evidence: `raw/m4_20260828_run01/`, `raw/m4_20260828_run02/` (`00_inputs.json`, `02_gated.jsonl`,
`03_nongated.jsonl`, `04_manifest.json` each); `work/m4_20260828_run01_smoke.json`,

## 2. GLIO-A01 — exact varying/clip-distance capacity and failure modes

### OBSERVED

**Varying-component ceiling = exactly 124 scalar components consumed by the fragment function**
(`raw/m4_20260828_run{01,02}/02_gated.jsonl`, family `vary_scalar`, 52 cases; `vary_dce`, 6 cases).
At `float` (1-wide) granularity: N=124 → `PIPELINE_OK`; N=125 → `PIPELINE_FAIL`,
`"Number of varying components(125) exceeds the limit (124)"`; N=126 → same message form with
"(126)"; **N≥127 → a different failure**, `"Compilation failed due to an interrupted connection:
XPC_ERROR_CONNECTION_INTERRUPTED. This error occurred after multiple retries."` (Metal's
out-of-process compiler backend service crashes rather than returning a validation diagnostic once
the overshoot is large enough). Re-tested N=8 and N=31 immediately after an N=32 crash in the same
run: both still `PIPELINE_OK` — rules out global service degradation; this is a reproducible,
deterministic per-N crash, not a stuck session.

The SAME 124-scalar ceiling was independently reached at every tested granularity:
`float4` (N=31→OK, N=32→FAIL, `vary_float4_n31`/`n32`), `float2` (N=62→OK i.e. 124 scalars, N=63→
126-scalar FAIL, `vary_float2_n62`/`n63`), `float3` (N=41→OK i.e. 123 scalars — the closest
float3-granularity can land under 124 — N=42→126-scalar FAIL, `vary_float3_n41`/`n42`), and `half`
(N=124→OK, N=125/126/127 → same message/crash split as `float`, `vary_half_n124..n127`). **The
budget is per scalar component, independent of declared vector width and independent of bit width
(half vs float) — never per-declared-struct-member ("slot") and never padded to 4-wide.**

**Declared-vs-consumed (DCE) sensitivity** (`vary_dce`, 6 cases): `declared=500, used=10` →
`PIPELINE_OK`; `declared=200, used=200` → `PIPELINE_FAIL`; `declared=150, used=124` →
`PIPELINE_OK`; `declared=150, used=125` → `PIPELINE_FAIL` ("...(125) exceeds the limit (124)").
**The budget counts only the varyings the fragment function actually reads (post-link liveness),
never the raw declared struct size** — an unlimited number of unread varyings may be declared for
free (structural convenience for a driver's IR, not a hardware cost).

**Clip-distance ceiling = exactly 8, an INDEPENDENT budget from the varying ceiling**
(`clip_sweep`, 14 cases at 1-unit granularity 0..10 plus 16/64/256; `vary_clip_combo`, 5 cases).
N=8 → `PIPELINE_OK`; N=9 → `PIPELINE_FAIL`, `"Number of clip planes used exceeds supported
maximum"` (this message never names an explicit number, unlike the varying one). **124 user
varyings AND 8 clip-distance components succeed simultaneously in the same pipeline**
(`combo_v124_c8` → `PIPELINE_OK`); pushing either past its OWN limit fails regardless of how far
under budget the other is (`combo_v124_c9` fails on the clip message; `combo_v125_c0` fails on the
varying message). Clip distance is never counted against, nor shared with, the 124-scalar varying
budget.

**`cull_distance` is not a recognized MSL attribute** (`cull_negative`, 1 case): the frontend
compiler emits `warning: unknown attribute 'cull_distance' ignored`, then (since the attribute is
dropped, leaving a bare `float[1]` array field) `error: invalid return type 'VOut' for vertex
function` / `field of illegal type 'float[1]' declared here` → `COMPILE_FAIL`. Cull distance
consumes **no** budget because it cannot be expressed at all.

**Silent-aliasing check (real draw + readback, not just pipeline creation)**
(`vary_render_confirm`, 4 cases): at the exact boundary (124 `float` scalars, 31 `float4` vectors =
124 scalars, 62 `float2` = 124 scalars, and a small control at 8), a real triangle draw summing
**every** declared varying and reading back the exact float32 result matched the host-computed
expected sum within float32 accumulation tolerance in all 4 cases, both runs
(`observed_sum`==`expected_sum` to 4 decimal places, e.g. `varyconfirm_float_n124`:
observed=0.7626, expected=0.76260000...01). **No aliasing was observed at maximum legal capacity —
the max-legal pipeline both creates AND executes correctly.**

### INTERPRETED

- **The observed failure mode at the boundary is REJECTION, not silent aliasing.** Both
  sub-questions the addendum asked ("rejected by Metal, rejected by pipeline/link state, aliases
  or wraps a slot, faults, or executes with another observable result") resolve to: **rejected by
  pipeline/link state** (`newRenderPipelineStateWithDescriptor:`), with a second, distinct,
  crash-shaped failure mode (compiler-service XPC crash) once the overshoot magnitude grows past a
  few components. Neither failure mode is a GPU fault or device loss; neither wedged the host.
- **This generalizes and extends EXP-G1a's `0x58000+0x2c = 4 + 4·nvary` formula** (HW-validated
  only for `nvary` 0..8, i.e. total UVS scalars 4..36, with `nvary` always float4-declared): the
  correct general form is **`0x58000+0x2c = 4 + total_user_varying_scalar_components`**, ceiling
  128 (4 position + 124 user), because this experiment shows the limit is counted per scalar
  component regardless of declared vector width. This is an `INFERRED` extension, not a fresh
  DATA-TRACE re-validation of the byte field itself at the new boundary — see §7 open items.
- **Both the API-advertised limit and the maximum simultaneously-exercised producer/consumer
  pipeline coincide at 124** (the `vary_render_confirm` family proves the boundary is not merely
  an API ceiling nobody can actually use — a real VS→FS pipeline at exactly 124 both compiles and
  computes correctly). The apparent hardware instruction-field width is wider (EXP-G1a's `0x57`
  varying-store 9-bit slot field structurally reaches 511) — this experiment does not attempt to
  bypass Metal's own validator via hand-assembled UVS stores (out of scope per the dispatch's
  explicit "no assembler needed" scoping for the capacity sweep; flagged as an open item, not
  silently assumed identical).
- Producer vs. consumer limits: this experiment tested only "VS declares more, FS reads fewer,"
  which succeeds and is DCE'd (a driver may over-provision Its IR freely). It did not test the
  inverse (FS `stage_in` requesting a varying the VS never wrote) — Metal's `stage_in` struct is
  necessarily a subset of what the VS output struct provides, since it is literally the same
  struct type in every kernel here, so that configuration is not constructible through ordinary
  MSL and was not pursued.

## 3. GLPRE-A03 — pre-raster special-output boundary behavior

### 3a. NaN / Inf / signed-zero clip-space positions (OBSERVED, `position_special`, 14 cases)

One vertex's clip-space position component perturbed, full-target (4×4) triangle, filled/total
pixel count against a fully-finite baseline control (`pos_baseline`: 16/16 filled, confirms the
harness/geometry itself is correct):

| component | value | filled/16 | category |
|---|---|---:|---|
| x | NaN | 0 | discard |
| x | +Inf | 0 | discard |
| x | −Inf | **16** | **full fill** |
| y | NaN | 0 | discard |
| y | +Inf | 0 | discard |
| y | −Inf | **16** | **full fill** |
| z | NaN | 0 | discard |
| w | NaN | 0 | discard |
| w | +0.0 | **16** | full fill |
| w | −0.0 | **16** | full fill (identical to +0.0) |
| w | +Inf | 6 | partial |
| w | −Inf | 0 | discard |
| w | −1.0 (finite, ordinary negative) | 1 | partial (near-total discard) |

Zero `CMDBUF_ERROR`/device-loss cases anywhere in this family, either run.

**INTERPRETED.** NaN in any tested component, and +Inf in x/y, cause whole-primitive discard — the
plausible, conservative behavior. **−Inf in x or y does NOT discard; it fills the entire target** —
a striking asymmetry, consistent with a clip/edge-function formulation under which a vertex driven
to negative infinity in a screen axis satisfies every half-plane test trivially rather than failing
one. **w=0 (signed both ways) renders full, not discarded** — relevant to real driver techniques
(e.g. skybox tricks deliberately using `w=0`); the perspective divide by exactly zero does not
poison the pipeline. The **signed-zero pair is confirmed bit-for-bit equivalent** in outcome (both
16/16), the expected IEEE-754-comparison-equal result, tested explicitly rather than assumed. w=+Inf
and w=−1.0 (an ordinary "behind the eye" finite negative w) both give partial/near-discard results,
distinguishable from the w=0 and w=NaN/−Inf cases — genuine intermediate clip outcomes, not a
crash-shaped or all-or-nothing response.

### 3b. Point size (OBSERVED, `point_size`, 20 cases, 600×600 target)

| requested size | outcome |
|---|---|
| 0.0, −0.001, −1e8, −Inf | **discard** (0 px) |
| 4, 16, 64, 128, 256, 510, 511 | **exact `size×size` centered square** (e.g. 511 → 511×511=261121 px, bbox centered at target center) |
| 512, 513, 1000, 1e8, NaN, +Inf | **clamped to the identical 511×511 centered footprint** (byte-identical bbox/count to the size=511 case) |
| −1, −5, −50 | **anomalous**: real (non-zero), reproducibly *square* coverage (90000/88804/75625 px = exact 300²/298²/275²) but **off-center**, offset toward +x,+y from the point origin — neither a clean discard nor a clean clamp-to-511 |

**INTERPRETED.** There is a genuine hardware/firmware **point-size clamp ceiling of 511 pixels**
(not 512, not device-max) — confirmed independent of viewport/target size in build-time probing
(re-tested on a 2000×2000 target: identical 511×511 footprint, ruling out target-edge clipping as
the explanation). **NaN and +Inf point sizes are silently clamped to this same ceiling, not
discarded and not producing garbage** — a driver may treat "size ≥ 511 or non-finite-positive" as
one clamp case. **Very-small-magnitude and very-large-magnitude negative sizes discard cleanly**
(matching the `size ≤ 0` semantic a driver would expect), but a **moderate negative-magnitude
band (roughly −1 to −50 in this sweep) produces a real, reproducible, but off-center square
footprint** that fits neither the discard nor the clamp model — recorded precisely as observed and
flagged as likely-undefined/implementation-specific behavior (root-cause not resolved; see §7).
**Recommendation to implementers: never emit a negative point size** — `0.0` (or clamping negative
requests to `0.0` in the driver) is the only well-behaved way to represent "no point," since the
hardware's own negative-size behavior is not clean.

### 3c. Out-of-range render-target-array-index / viewport-array-index (OBSERVED, `layer_oob`
13 cases + `viewport_oob` 8 cases)

| mechanism | in-range (0..N−1) | first OOB (N) | far OOB (255, 2³²−1) |
|---|---|---|---|
| `[[render_target_array_index]]`, N=4 | lands at requested index | lands at **layer 0** | lands at **layer 0** |
| `[[render_target_array_index]]`, N=8 | lands at requested index | lands at **layer 0** | lands at **layer 0** |
| `[[viewport_array_index]]`, N=4 | lands at requested index | lands at **viewport 0** | lands at **viewport 0** |

Every in-range control (0,1,2,3 for N=4; 7 for N=8) landed exactly at its own index in both runs;
every tested OOB value (4, 5, 8, 255, 4294967295) landed at index 0, for both mechanisms, at both
tested layer counts.

**INTERPRETED. Both mechanisms clamp any out-of-range index to exactly index 0** — not
clamp-to-maximum (N−1), not modulo/wrap of the declared count, and not primitive discard. This is
the same policy for both `render_target_array_index` and `viewport_array_index`, and is independent
of the declared array/viewport count (4 vs 8 both clamp to 0). A driver targeting Vulkan/GL
semantics (where an out-of-range layer/viewport index is application error / undefined, but some
APIs specify wrap or clamp-to-max) must know Apple9 hardware/Metal's actual policy is
**clamp-to-zero**, not clamp-to-max, if it ever needs to reason about worst-case behavior for an
unvalidated shader-computed index.

### 3d. Provoking-vertex convention (OBSERVED, `provoking`, 3 cases)

- **List, direct fetch order** (vertex_id 0,1,2 in that order): center pixel = **red** = the
  color written for vertex_id 0.
- **List, reversed index buffer** (`indices=[2,1,0]`, so the FIRST vertex fetched for this
  primitive has vertex_id 2, not 0): center pixel = **blue** = the color for vertex_id 2, i.e. the
  color tracks *which vertex was fetched first*, not a fixed "`vertex_id==0`" special case.
- **Triangle strip, 4 vertices → 2 triangles**: first triangle's sample = **red** (vertex 0, that
  triangle's own first window vertex); second triangle's sample = **green** (vertex **1**, that
  triangle's own first window vertex — NOT vertex 3, which would be the newest/last-added vertex).

**INTERPRETED — GLPRE-A03's provoking-vertex sub-question, resolved as a Metal-exposure-boundary
negative result.** Apple9/Metal fixes the provoking vertex to **the first-fetched vertex of each
assembled primitive** (the Direct3D/Vulkan `VK_PROVOKING_VERTEX_MODE_FIRST_VERTEX_EXT`-style
convention), consistently across plain lists, reordered-index lists, and strips (each strip
triangle's own first window vertex, confirming the rule is per-primitive, not
per-whole-draw-first-vertex-only). **Metal exposes no API to select a different convention** — no
searchable analogue of `VK_EXT_provoking_vertex`/`glProvokingVertex` was found in the public Metal
render-pipeline/render-command-encoder surface used by this harness (`MTLRenderPipelineDescriptor`,
`MTLRenderCommandEncoder`). This is recorded as a first-class **negative** result per the dispatch
brief: **an implementer targeting OpenGL's default `GL_LAST_VERTEX_CONVENTION` (last-vertex flat
shading) cannot configure the hardware/Metal to do it directly and must emulate it** — the standard
technique is to rewrite/rotate the index buffer (or duplicate the flat-shaded attribute onto
whichever vertex must appear first) so that, under the hardware's fixed first-vertex rule, the
value that should provoke ends up in the first-fetched slot of each primitive. This adds a concrete,
per-primitive index-buffer transformation to the software `poly`/GL-emulation surface already
tracked for this driver.

## 6. What Metal does/does not expose (emulation summary for implementers)

- **Exposes, with hardware-backed exact limits**: user-varying scalar budget (124, per-component),
  clip-distance budget (8, independent), point-size clamping (511 ceiling, NaN/+Inf-safe),
  layer/viewport-index clamp-to-0 on OOB.
- **Does NOT expose (must be emulated in software)**:
  - **Cull distance** — no MSL attribute exists; must lower to clip-plane-equivalent logic or a
    manual discard/vertex-rejection scheme (matches the existing `docs/cmdstream/README.md` note).
  - **Alternate provoking-vertex convention** (OpenGL default last-vertex) — no API surface found;
    must rewrite/rotate index buffers or duplicate flat-attribute values so the desired vertex is
    always first-fetched under the hardware's fixed first-vertex rule.
  - **A different point-size/layer/viewport OOB policy** than what the hardware does natively (e.g.
    a Vulkan driver wanting clamp-to-max instead of clamp-to-zero for an out-of-range layer index)
    would need its own shader-side range check before writing the sysval output, since the hardware
    will not do that clamping for it.

## 7. Open items (not silently omitted)

1. `0x58000+0x2c`'s exact byte value at the new 124-scalar boundary is not independently
   re-confirmed by a fresh DATA-TRACE (`iotrace`) capture in this experiment; the generalized
   formula `4 + total_scalar_components` (ceiling 128) is `INFERRED` from EXP-G1a's
   `HW-VALIDATED` `nvary`-0..8 formula plus this experiment's own API-level component-counting
   evidence, not a fresh byte-level HW-VALIDATED result for the boundary itself.
2. The anomalous mid-negative point-size footprint (§3b) is recorded as-observed; no formula was
   derived, and the exact transition points between "discard" and "anomalous" and between
   "anomalous" and (if it exists) "clamp" were not exhaustively bisected.
3. Metal API surface search for a provoking-vertex control was not exhaustive beyond
   `MTLRenderPipelineDescriptor`/`MTLRenderCommandEncoder` (the obvious candidates); a documented
   negative, not a proof of absence across the entire framework.
4. Only `float`/`half`/vector widths were tested for the varying budget; packed/atomic or
   integer-typed varyings (`int`, `uint`, `short`, etc., all legal MSL varying types) were not
   separately swept — no reason from the observed per-component-count model to expect a different
   ceiling, but not directly tested.
