# EXP-0084 pre-registration — M4 dynamic buffer addressing (MEM-20/21/22)

**Frozen state: PRE-GPU.** No Metal compilation, no `tools/shdump` invocation,
and no GPU dispatch has occurred for EXP-0084 at freeze time. The only
host-side activity so far: `xcrun clang` compiled `harness/probe.m` and
`harness/splice_run.m` in a throwaway scratch directory (since deleted) to
prove they link, and each was executed with **no arguments**, which exits 2
at argument validation *before any Metal call* (`ARGS_FAIL`, matching the
`EXP-0076` precedent of a link-only pre-registration build). `kernels/
cap_kernels.metal` was generated by the frozen `kernels/gen_cap_kernels.py`
and diffed byte-for-byte against the committed file — a pure-Python text
generation step, no compiler, no device. Nothing else has touched Metal, the
GPU, or `tools/shdump`/`tools/agx-isa`/`tools/agxtest` beyond reading their
(already-public, already-committed) source and `db.json` as reference
material. This registration precedes the build execution and the two capture
runs.

## Question

Part-II questionnaire items **MEM-20, MEM-21, MEM-22** of
`APPLE9_RE_IMPLEMENTATION_GAPS.md` ("P0 — Memory addressing and robustness"),
the bindless/descriptor-array blockers for a Vulkan-grade compiler:

- **MEM-20** — can Apple9 load/store through a 64-bit device address obtained
  dynamically in a GPR or register pair, without first assigning that address
  to a statically encoded base slot? A `Yes` supplies the indirect/bindless
  fallback for descriptor arrays and shaders whose logical resource count
  exceeds the direct-slot capacity.
- **MEM-21** — can a non-uniform, per-lane descriptor-array index select
  different buffer base addresses for different lanes in one SIMD group,
  distinguished from a uniform-program selection that picks one address for
  the whole dispatch?
- **MEM-22** — when given more live buffer resources than fit the direct-slot
  path, does the toolchain reject, use a descriptor-table/dynamic-address
  path, or split/preload? Compiler-output observation answers WHICH strategy
  is chosen; the selected fallback still needs independent hardware
  execution validation.

Prior, adjacent, already-established context (not re-derived here, cited for
scope only): `docs/cmdstream/README.md` "Argument buffer (Tier-2) — decoded
(EXP-0011)" and `docs/descriptors/README.md` document, from DATA-TRACE
evidence (our own process's IOKit traffic + BO contents, not Apple binary
introspection), that Apple's own Tier-2 argument-buffer substrate stores an
**inline 8-byte GPU VA per bound buffer slot**. `experiments/
EXP-0078-m4-base-slot-census/` (QUARANTINED, non-promoted — its raw run 01
is retained as process history only, no MEM-15/16/17 claim) recorded a
**hypothesis, not a fact**, that at least 31 device-buffer base slots are
simultaneously usable via direct `[[buffer(N)]]` binding on M4, and that
slots past the populated edge silently read zero rather than fault; this
experiment's `mem22_direct_cap_31`/`mem22_direct_cap_32` cases independently
re-establish (or refute) the 31-argument boundary as a **fresh, separately
gated observation**, not an inherited claim. `tools/agx-isa/db.json`'s
`device_load`/`device_store` descriptors (HW-VALIDATED, EXP-0012 +
RT-1a-FIX + EXP-M4-13) already establish that the instruction's memory
address is computed as `(index_reg + idx_off) * unit`, **`base = buffer
[base_slot]`** where `base_slot` is an 8-bit **immediate** field (encoded
once, at compile time, identical for every lane by construction) and
`index_reg` is an 8-bit **register-select** field (a genuine per-lane GPR
read). This structural fact is the basis for H3 below: `base_slot` is
architecturally incapable of per-lane divergence; any true per-lane base-
address divergence must come from `index_reg`, if the address itself lives
in registers rather than solely in the `buffer[]` table.

Compiler consequence recorded, not implemented here: a `Yes` on MEM-20/21
identifies the concrete NIR/instruction-selection lowering a Vulkan
descriptor-array `nir_intrinsic_load_vulkan_descriptor` /
`nir_deref_instr`-chased bindless access must target; a `No` requires
identifying the real fallback (SW re-binding per lane, a hardware descriptor
table, etc.) before that lowering can be written.

## Hypotheses (falsifiable; refuters are per-case, recorded verbatim)

On this machine (Apple M4 / G16G, macOS 26.6.2 build 25G82, Metal 4), for
MSL authored by us (`kernels/probes.metal`, `kernels/cap_kernels.metal`),
compiled at runtime with `MTLCompileOptions.fastMathEnabled = NO` and
`mathMode = MTLMathModeSafe`, every dynamic device address obtained ONLY
through public Metal mechanisms (`MTLBuffer.gpuAddress`, a public property;
`MTLArgumentEncoder`, the public implicit-argument-buffer API):

- **H1 (MEM-20, core).** A kernel that reads a 64-bit value from an ordinary
  `device ulong*` buffer at runtime and dereferences it as a `device T*`
  pointer (`mem21_uniform`/`mem20_uniform_single`, N=1: every backing buffer
  the kernel ever touches is bound ONLY by its address appearing as *data* in
  `addrs[]`, never via `setBuffer:offset:atIndex:`) compiles, dispatches
  without a command-buffer error, and every lane reads the correct tag word
  through that address. Refuter: compile failure, a non-4 command-buffer
  status, a hang/watchdog, or any lane's `out_hex` word differing from the
  frozen `TAG(0) = 0x5A000000`.
- **H2 (MEM-20, independent methods).** The SAME capability, reached two more
  independent ways: (a) Metal's implicit argument buffer (`mem20_implicit_ab`,
  a struct member `device uint *ptr`, populated via `MTLArgumentEncoder` —
  never via `setBuffer:offset:atIndex:` on the pointee); (b) double
  indirection (`mem20_chained`: a dynamic address that itself points to a
  buffer holding a second dynamic address). Refuter: either construct fails
  to compile, faults, or returns anything but the frozen expected tag
  pattern (`TAG(0x300000+i)` for (a), `TAG(0x700000+i)` for (b), i=0..31).
- **H3 (MEM-21, uniform vs. divergent).** `mem21_uniform_ctrl` (N=2, `sel_u`
  a scalar `constant uint&` argument, identical for every lane by
  construction — it cannot vary per lane in MSL) makes **every** lane read
  the SAME buffer (`out_hex` = 32 repeats of one tag word) — the uniform-
  program-selection negative control. `mem21_perlane_divergent_32` (N=32,
  selector = `gid % N` computed ONLY from `thread_position_in_grid`, never
  read back from a per-lane data buffer) makes **each of the 32 lanes in one
  SIMD group** (M4 SIMD width 32, `EXP-0018`/established elsewhere in this
  repo) read a DIFFERENT buffer, `out_hex[gid] == TAG(gid)` for every
  gid — i.e. 32 DISTINCT tag words, not one value broadcast 32 times.
  `mem21_outlier_lane17` (N=2, `sel = (gid==17) ? 1 : 0`) makes lane 17
  alone read `TAG(1)` while every other lane reads `TAG(0)` — the
  fine-grained single-lane control that refutes a "coarse broadcast-group"
  alternative explanation for H3's perlane result. Refuters: the uniform
  case shows ANY two lanes with different tags; the perlane case shows ANY
  two lanes (that selected different `sel`) with the SAME tag, or fewer
  than 32 distinct tag words present; the outlier case shows any lane other
  than 17 reading `TAG(1)`, or lane 17 reading `TAG(0)`.
- **H4 (MEM-20, residency).** `mem20_no_useresource` (identical to H1's N=1
  case, but the compute encoder never calls `useResource:usage:` on the
  indirectly-referenced backing buffer) is an **adversarial/boundary**
  probe with NO directional prediction pre-registered either way: it is
  legitimate hardware-probing evidence whichever way it falls (a matching
  `TAG(0)` readback would mean unified-memory residency tracking is not
  required for a plain compute dispatch against a buffer never independently
  freed/reused; a fault, hang, wrong value, or command-buffer error would
  mean explicit residency declaration is load-bearing on this hardware — an
  UNDEFINED-BEHAVIOR-per-Apple's-public-docs outcome we are entitled to
  observe under the "hardware probing" allowed technique). Recorded
  verbatim either way; not used to answer MEM-20/21/22 on its own.
- **H5 (MEM-22, direct-slot boundary).** `mem22_direct_cap_31` (31 direct
  `[[buffer(N)]]` arguments, indices 0..30 — the known-achievable shape)
  compiles and dispatches cleanly, each `out[k-1] == bk[0]`'s own tag.
  `mem22_direct_cap_32` (indices 0..31, ONE more direct buffer argument) is
  the actual MEM-22 boundary observation: EITHER outcome (clean compile+
  correct dispatch, OR a recorded compile rejection with the compiler's
  error text) is a first-class, fully informative result — this hypothesis
  has no directional prediction; `harness/probe.m` is built to record a
  compile rejection as `compile_ok=false` (a normal case outcome, not a
  process fault) for exactly this reason.
- **H6 (MEM-22, dynamic-address fallback).** `mem22_dynamic_64` (N=64) and
  `mem22_dynamic_256` (N=256) — both far beyond H5's ≤32 direct ceiling —
  reuse H3's per-lane mechanism (`mem21_perlane`) with `N` = the dispatch
  grid size, `sel=gid` (an identity permutation: lane k reads buffer k).
  Both compile, dispatch cleanly, and every lane reads its own distinct
  tag. This is the hardware-execution half of MEM-22: it shows the SAME
  dynamic-address mechanism validated in H1/H3 is what carries a resource
  count that direct binding provably cannot (H5). Refuter: any lane's tag
  wrong, a command-buffer error, a hang, or fewer than N distinct tags
  present in `out_hex`.
- **H7 (mechanism decode).** Tokenizing (`tools/agx-isa`, our own DB, read-
  only) the compiled `splice_target` kernel's `_agc.main` (+ its preamble
  `_agc.main.constant_program` if present) finds **at least two**
  `device_load` instructions in the MAIN region whose **`index_reg` fields
  differ** — the two per-lane dereferences `vA=pA[gid]`/`vB=pB[gid]`, which
  cannot be hoisted to the preamble because they depend on `gid`. This is
  the pre-registered **identification algorithm** (below); its refuter
  (`confirmation_ok=False`: fewer than 2 main-region `device_load`
  instructions, or the last two share one `index_reg`) is itself a
  recorded, non-fatal result (`status=identification_failed`) that answers
  H7 negatively without invalidating H1-H6 (which do not depend on H7).
- **H8 (splice, independent-encoding-synthesis).** Given H7 confirmed:
  splicing EXACTLY ONE byte — the `index_reg` field of whichever of the two
  identified loads the UNMODIFIED archive's baseline execution shows feeds
  `out` — from its own value to the OTHER load's `index_reg` value, and
  re-executing the SAME archive (forced from the archive's own machine code
  via `MTLPipelineOptionFailOnBinaryArchiveMiss`, the established
  `tools/agxtest` technique, EXP-0003/EXP-0005), makes `out` read the OTHER
  load's tag while `outb` is byte-identical to the baseline. This is the
  strongest evidence tier (`HW-VALIDATED`, independently synthesized
  encoding, not merely tokenized): it proves `index_reg` genuinely, causally
  selects which dynamically-loaded 64-bit value a `device_load` dereferences,
  independent of what the compiler originally wired. Refuter: `out`
  unchanged, corrupted, a fault, a hang, or `outb` changed (recorded
  verbatim as `outcome=refuted`; a `PIPELINE_MISS`/`ARCHIVE_FAIL`/crash is
  recorded as its own distinct outcome, never coerced into "confirmed" or
  silently retried).

Independent variable: which of the 12 dispatch-kind cases / 1 decode-kind
case / 1 splice-kind case (below). Controlled variables: MSL source, compile
options, buffer/tag geometry, dispatch geometry, single-thread-per-address
correspondence (`sel=gid` or `sel=gid%N`), and the harness process model
(one fresh process per case, exactly as `EXP-0076`).

Known confounders and honest limits (pre-registered, not corrected):

- **Compiler freedom.** The Metal compiler may lower `(device T*)(ulong
  value)` (and the implicit-AB/chained forms) to any instruction sequence;
  H1-H6 observe the BEHAVIOR of these frozen MSL idioms through the public
  API, not a claimed unique native encoding. H7/H8 observe the ACTUAL
  encoding for this ONE compiled kernel/toolchain/OS build only.
- **`index_reg` semantics are ISA-DB-documented (HW-VALIDATED, EXP-0012 +
  RT-1a-FIX) as "the GPR holding the array INDEX", not literally "the GPR
  holding the full 64-bit address".** H7/H8 test the STRONGER hypothesis
  that for `splice_target`'s specific compiled form, the relevant
  `device_load`'s effective address reduces to (a GPR-held value that
  equals) the dynamically loaded pointer — i.e. `base_slot`'s table entry
  and `idx_off`/`unit` combine to an identity/pass-through for this
  emitted form. This is NOT assumed; H8's splice is exactly the falsifiable
  test of it, and `PROVENANCE.md`/`RESULTS.md` will state precisely what
  was and was not established (a splice-validated fact about THIS compiled
  sequence is not automatically a general architectural rule for every
  `base_slot` value).
- **Register allocation is compiler-chosen, not authored.** H7's
  identification algorithm locates the target field by STRUCTURAL POSITION
  (last two main-region `device_load`s) and by the OBSERVED BASELINE
  execution (which tag lands in `out`), not by an a-priori assumption that
  source order equals program order — this is deliberate, to survive
  compiler reordering (see "Splice identification algorithm" below).
- **`mem22_direct_cap_32`'s outcome is unknown at freeze time by design**
  (H5); MSL's public per-stage buffer-argument limit for this device/OS/
  Metal version is not independently re-derived from any source other than
  this experiment's own compile attempt.
- The GPU-side behavior is measured through the public API and our own
  `tools/shdump`/`tools/agx-isa`/own splice harness only; no kernel/
  firmware/Apple-binary introspection occurs anywhere in this experiment.
- Scope is the **local M4 (G16G) only** (per `CLAUDE.md`/`CODEX.md` current
  target discipline); no A18 Pro (G17P) claim, no cross-target inference.

## Splice identification algorithm (frozen; `analysis/decode_lib.identify()`)

Given `splice_target`'s tokenized MAIN region (`_agc.main`) and PREAMBLE
region (`_agc.main.constant_program`, possibly empty) instruction lists (in
program order, each annotated with its cumulative byte offset within its own
region):

1. Filter each region's instruction list to `mnemonic == "device_load"`.
2. `confirmation_ok` REQUIRES at least 2 `device_load` instructions in the
   MAIN region. `l1`, `l2` = the LAST TWO main-region `device_load`
   instructions, in program order (the two per-lane dereferences `vA=
   pA[gid]`/`vB=pB[gid]` MUST be in main, not preamble, because they depend
   on `gid`; the two OUTER loads that fetch the pointer VALUES from
   `addrs[0]`/`addrs[1]` may or may not be hoisted to preamble, and this
   algorithm does not need to locate them).
3. `confirmation_ok = (l1.index_reg != l2.index_reg)` — there must be
   something to swap.
4. If `confirmation_ok`, `decode_case.py` reports `l1`/`l2` (offset,
   `base_slot`, `index_reg`, `addr_mode`, `idx_off`, destination-register
   composite) verbatim as H7's answer; no splice occurs in the decode-kind
   case.

## Splice case procedure (frozen; `analysis/splice_case.py`)

1. Build the SAME `splice_target` archive; re-run `identify()` (byte-
   identical result expected — the same compile, same algorithm).
2. Run the UNMODIFIED archive via `splice_run` (baseline). REQUIRE its
   `out_hex` to be uniformly `TAG_A = 0x5A0000AA` or uniformly `TAG_B =
   0x5A0000BB` (32 repeats) and `outb_hex` to be the OTHER tag, uniformly
   — any other baseline shape is `outcome=baseline_unexpected_tags`, a
   pre-capture-equivalent STOP for this case (H1-H6 remain unaffected).
3. `target` = whichever of `l1`/`l2` the baseline shows feeds `out` (`l1`
   if `out_hex` is all `TAG_A`, else `l2`) — grounded in the OBSERVED
   baseline, not assumed source/program order. `other` = the remaining one.
4. Absolute splice file offset = `agxparse.py --locate _agc.main`'s
   `ABS_OFF` + `target.offset` (the instruction's offset within `_agc.main`)
   + 5 (the `index_reg` field is `device_load` bits [40:48], i.e. byte
   offset 5 within the 14-byte instruction — `tools/agx-isa/db.json`,
   HW-VALIDATED). PRECONDITION check: the byte currently at that absolute
   offset must equal `target.index_reg`'s own value, else
   `outcome=splice_precondition_failed` (a defensive STOP, not a silent
   overwrite).
5. Splice that ONE byte to `other.index_reg`'s value; write a SEPARATE
   spliced archive file (the original is never mutated).
6. Run the spliced archive via `splice_run`. Predicted refutable outcome:
   `out_hex` now uniformly reads the tag `other` would have produced (the
   OPPOSITE of the baseline's `out_hex`), `outb_hex` is BYTE-IDENTICAL to
   the baseline's `outb_hex` (the untouched load is unaffected) →
   `outcome=confirmed`. Any other observed shape (unchanged, corrupted,
   `outb` also changed, `PIPELINE_MISS`/`ARCHIVE_FAIL`, a command-buffer
   error, a process fault) → `outcome=refuted` or a more specific failure
   tag — recorded verbatim, never coerced.

## Per-case record schema (frozen; ONE authoritative key set per kind)

- `DISPATCH_CASE_KEYS` (17 keys: `i, name, kind, mode, function, n, sel, k,
  use_resource, status, exit, timed_out, compile_ok, dispatch_ok, cb_status,
  out_hex, outb_hex, outsel_hex`) — NO timing field, NO device/OS field, NO
  address field. `out_hex`/`outb_hex`/`outsel_hex` are TAG words (compile-
  time-chosen 32-bit constants, e.g. `0x5A000000|k`), never a GPU address.
- `DECODE_CASE_KEYS` (23 keys, flattened `l1_*`/`l2_*` instruction-field
  values — byte offsets WITHIN a fixed compiled binary, small register-
  number/enum fields, never a runtime address) plus `confirmation_ok`.
- `SPLICE_CASE_KEYS` (17 keys) — `splice_offset_abs` is a byte offset within
  the compiled archive FILE (deterministic given fixed source), not a GPU
  virtual address; `target_index_reg`/`other_index_reg`/`splice_from`/
  `splice_to` are 8-bit register-select field VALUES (0-255), not
  addresses.
- Statuses (frozen enum, shared across kinds): `ok, compile_reject,
  cb_error, identification_failed, baseline_failed, refuted, confirmed,
  watchdog, proc_fail, proc_timeout`.
- `05_receipts.jsonl`: one full process receipt (9-key `procutil.rec()`
  schema + `i,name,kind`) per case — includes `stdout`/`stderr`/timing;
  NOT byte-compared across runs (this is where any incidental
  nondeterminism, e.g. a differing `library_compile_seconds` inside a raw
  stdout capture, is allowed to live — never in `04_results.jsonl`).

## Cross-run gate (frozen; the direct fix for the EXP-0081 quarantine class)

`raw/<run>/04_results.jsonl` must be **BYTE-IDENTICAL, in full, between
run01 and run02 — no carve-out for any case.** This is stronger than
`EXP-0076`'s in-bounds-only policy because EXP-0084's gated schema contains
**no field that can legitimately vary run-to-run for a fixed source**: no
timing, no GPU virtual address (never captured anywhere — see
`no_address_fields_check()` in `verify.py --selftest`, which both greps
`harness/*.m` for any print of a `gpuAddress` value and asserts no frozen
key set names an address-shaped field), no pid, no allocator-dependent OOB
behavior (unlike EXP-0076's robustness matrix, nothing here probes
allocator/out-of-bounds nondeterminism — every dynamic address dereferenced
in this experiment points at a buffer WE allocated and control the exact
size of). `verify.py --selftest` proves this gate PASSES on a synthetic
byte-identical pair and FAILS on a synthetic pair differing in exactly one
case's `status` field, using the SAME comparator `run.py`'s captured-state
gate uses (`captured_gate()`, imported, never reimplemented).
