## Per-item plan and coverage decision

Format: **ITEM — verbatim question.** Hypothesis. Plan. Coverage: COVERED (this
experiment runs real HW cases) or DEFERRED (why, and the follow-up it needs).

**CF-01 — Can arbitrary reducible NIR `if`/`else` control flow be expressed using
the decoded predicate and reconvergence operations?**
Hypothesis: yes for the corpus of reducible shapes already decoded
(if/else/diamond/elseif-chain/if-in-else), using either the predication path
(compare+select, no branch) or the branch path (`icmp_pred`+`if_push`/
`jump_cond`+`pop_reconverge`) depending on whether the region contains a
`return`/`break`/`continue`. Refuter: any shape that leaves undecoded tokenizer
residue, or that a compiler needs but our decoded op set cannot express.
Plan: compile+tokenize+HW-run a diamond join, a 5-way if-elseif chain, an
if-nested-in-else, and reuse `predalias`'s two-nested-loop shape as an explicit
**predication-vs-branch boundary probe**. Verify every shape tokenizes with 0
leftover AND matches a host oracle. **Coverage: COVERED**
(`cf_shape_diamond`/`cf_shape_elseif`/`cf_shape_if_in_else`/`cf_predalias_baseline`
+ the CF-03 depth sweep below, which is itself a large if/else corpus).

**CF-02 — Can arbitrary nested NIR loops with `break` and `continue` be expressed
without an undocumented compiler-generated helper sequence?**
Hypothesis: yes, `break`/`continue` compose in one data-dependent loop without a
hidden helper op (extending EXP-0010/RT-1b's separate break-only/continue-only
corpus to BOTH in the same loop). Refuter: undecoded tokenizer residue, or the two
combined skipping the wrong iteration. Plan: one authored kernel with `continue`
at `k==3` and `break` at `k==7` in the same loop; HW-run + host oracle.
**Coverage: COVERED** (`cf_shape_break_continue`); nested-loop depth (multiple
loop levels) is covered under CF-03 instead (that is what "nested" stresses
structurally).

**CF-03 — Is the maximum safe hardware reconvergence nesting depth known?**
Hypothesis: unknown a priori; the compiler accepts arbitrarily deep nesting at
compile time (no compiler-side cap), so any limit is a hardware/silicon
boundary, expected either as a clean fault/wrong-result transition or as no
observed limit within a practical tested range. Refuter: a depth where output
silently corrupts, faults, or hangs while a shallower depth is correct.
Plan: three orthogonal sweeps (generated by `harness/gen_cf_kernels.py`, frozen
depths in `harness/matrix.py`): (a) `ifnest_{1..128}` -- nested divergent-return
if-chains, per-lane genuinely divergent exit depth (value vs. per-level
threshold); (b) `loopnest1_{1..64}` -- pure nested-loop STRUCTURAL depth with
trip count pinned to 1 (data-dependent, so not provably foldable, but total
work stays O(1) per thread regardless of depth -- isolates nesting depth from
total iteration count so depth can be pushed far without a runtime blowup);
(c) `loopnestD_{1..12}` -- nested loops with a genuinely per-lane-divergent
trip count in {1,2,3} (`(thread_position_in_grid % 3) + 1`), to confirm
REAL divergence (not just structural depth) still reconverges correctly at
multiple simultaneous nesting levels. Each case: HW dispatch + exact host
oracle (int32-wrapping where applicable) + finite-resource row (first-invalid
depth if any is observed, else "no failure observed up to tested max").
**Coverage: COVERED.**

**CF-04 — Does divergent return require a distinct lowering from an ordinary
branch to a shared epilogue?**
Hypothesis: EXP-0010 established that a single early return under divergence
compiles to predicate+mask machinery with NO explicit `0x8f` RET/frame marker
(that marker is reserved for real subroutine CALL/RETURN, EXP-0035); the
per-kernel "return" instead just narrows the execution mask so the remaining
code (implicitly the epilogue) runs masked. Refuter: an early-return kernel
that DOES emit the `0x8f` call-frame marker, or multiple return points that do
NOT converge on one shared store/epilogue. Plan: (1) `structural_pair` compile
diff of `ret_early` (has a `return`) vs `plain_join` (semantically identical
values, no `return`) -- do they differ, and does either carry a call-frame
marker; (2) `multi_return` -- THREE early-return points at three different
nesting depths converging on the SAME final store, HW-run against a 5-way host
oracle. **Coverage: COVERED.**

**CF-05 — Are Boolean predicates stored in an independently addressable
predicate file rather than ordinary GPR values?**
Hypothesis (pre-registered, falsifiable both ways): `tools/agx-isa/db.json`'s
`icmp_pred` descriptor already types byte0's HIGH NIBBLE as `dst_pred` (a 4-bit
field, `EXP-M4-13`, compile-only/byte-diff, never HW-splice-tested). Two
competing models: (A) it is a real, independently addressable multi-entry
predicate file (like a GPR file) that a register allocator could target at
arbitrary indices; (B) it is a fixed/implicit single slot that the immediately-
following `if_push` always reads regardless of the encoded nibble, i.e. NOT a
general allocatable namespace. Refuter for (A): splicing `dst_pred` to a
nonzero value still produces CORRECT, differently-routed output (the consumer
demonstrably reads the addressed slot). Refuter for (B): ditto -- if nonzero
values behave identically to 0, or fault, that is evidence against a plain
"always slot 0" model too and must be reported honestly either way.
Plan: (1) compile+tokenize `ifnest_004`/`ifnest_016`/`shape_if_in_else` and
record the `dst_pred` field's ACTUAL compiler-emitted value across 18+
occurrences (structural, compile-only); (2) HW-splice `ifnest_004`'s first
`icmp_pred`'s `dst_pred` nibble to {1, 5, 0xf} and observe the DOWNSTREAM
(not the spliced instruction's own) output, per
`docs/isa/register-move-and-liveness.md`'s silent-zero-not-fault precedent.
**Coverage: COVERED.**

**CF-06 — Are all predicate-file allocation and lifetime restrictions known well
enough for a register allocator or late predicate allocator?**
Hypothesis: this is answered TOGETHER with CF-05 by the same evidence, not by a
separate kernel -- if CF-05 finds a real multi-entry addressable file, CF-06
asks for its capacity/lifetime; if CF-05 finds a fixed/implicit single slot
(model B), CF-06's answer degenerates to "there is no allocator decision to
make; always emit index 0, exactly as observed compiler output does." Refuter:
same splice evidence as CF-05, plus the CF-03 depth sweep's own compiler-
emitted `dst_pred` census (does it ever vary with nesting depth, up to 128
levels?). Plan: reuse the CF-03 `ifnest_*` sweep's tokenize output as a
census of `dst_pred` across 1..128 nesting levels (no separate kernel needed);
combine with the CF-05 splice result. **Coverage: COVERED** (evidence shared
with CF-05 and CF-03 by design, not a separate case group; tagged
`CF-05/CF-06` in the matrix).

**Branch reach and target encoding** (named in the dispatch's core-questions
paragraph; not itself a numbered CF-* item, tracked as `CF-01/02-reach`).
Hypothesis: `db.json`'s `jump`/`jump_cond` descriptors claim a 48-bit signed
byte-relative offset (EXP-0010 validated one point at -44; RT-1b validated one
point at -262/-104/-124 for CALL). The PRACTICAL enforced range is expected to
be far narrower than 2^48 -- bounded by the actual code-buffer/USC-window
size, not the encoding width -- so small perturbations near a valid target
should fault cleanly while huge magnitudes may fault differently or hang.
Refuter: a huge-magnitude offset that runs to completion with a sane result
(would falsify "bounded by code size"), or a small perturbation that does NOT
fault (would falsify "target must land on an instruction boundary").
Plan: locate `reach_loop`'s real backward-jump `jump` instruction by
tokenizing the compiled bytes (not a hardcoded offset -- the locate step is
part of the harness, `run.py:do_locate_splice`), then splice its 48-bit offset
field by six deltas: small forward/backward (±8B, plausibly still decodes as
SOME valid-looking target), mid forward/backward (±4096B), huge forward/
backward (±0x400000B). Hard per-case timeout (8s GPU + 12s host) since a bad
jump target can hang; a HANG is a valid, safely recorded result (own process,
contained). **Coverage: COVERED.**

**SIMD-01 — Is the executable subgroup width always 32 for every supported
Apple9 stage and launch shape?**
Hypothesis: yes for compute at every tested launch shape, INCLUDING a
threadgroup size that is not a multiple of 32 (a genuinely untested case in
prior work) -- the `threads_per_simdgroup` special register is expected to
report the FIXED architectural constant 32 even for a partial/final
simdgroup that only has 16 real threads, not the real occupancy. Refuter: a
partial group reporting 16 (occupancy-aware) instead of 32, or lane-index
wraparound not resetting cleanly at the threadgroup boundary. Plan:
`width_report` at tg=64 (2 full groups, sanity) and tg=48/grid=96 (1 full +
1 sixteen-thread partial group), reading `thread_index_in_simdgroup`,
`threads_per_simdgroup`, `simdgroup_index_in_threadgroup`,
`thread_index_in_threadgroup` for every thread. Fragment-stage width is
DEFERRED (see below). **Coverage: PARTIAL/COVERED for compute; DEFERRED for
fragment/vertex stage width** -- the fragment cases in this experiment (4x4
render target, SIMD-05/07) happen to show `simd_active_threads_mask()`
popcount = 16 for a full (undiscarded) 4x4 target, informally consistent with
one 32-wide group holding all 16 real fragments, but this experiment does not
run a dedicated fragment-stage width sweep across multiple target sizes/tile
boundaries; flagged as a named follow-up, not silently dropped.

**SIMD-02 — Are subgroup ballots exactly 32 bits with one stable bit-to-lane
mapping?**
Hypothesis: yes, `simd_ballot(pred)` returns a value whose low 32 bits are a
bitmask with bit `i` = predicate(lane i), stable and identical as read back
by every lane in the group. Refuter: any lane reading a DIFFERENT mask value
than its groupmates, or a bit position not matching `thread_index_in_simdgroup`.
Plan: `ballot_map` with three GENUINELY divergent predicates derived from
`thread_position_in_grid` (`i%3==0`, `i%7<2`, `5<=i<19`) -- not a uniform
compile-time-constant predicate, which would prove nothing about per-lane
mapping. grid=32/tg=32 (exactly one simdgroup); every one of the 32 lanes'
readback compared against a per-lane-computed host oracle bit. **Coverage:
COVERED.**

**SIMD-03 — Do subgroup shuffle, broadcast, rotate, and fill operations define
out-of-range lanes in the way required by NIR?**
Hypothesis: unknown a priori (this is the primary target of the finite-
resource mandate for this item) -- competing candidate behaviors are
modulo-32 wraparound, clamp-to-31, pass-through (return own value), zero, or
undefined/nondeterministic garbage. Refuter: any candidate model is refuted by
one counterexample in the swept range; nondeterminism (same input, different
output across the two runs) refutes ALL deterministic models and must be
reported as such, not hidden. Plan: `shuffle_dyn` (dynamic per-lane `ushort`
index from a buffer, so the compiler cannot compile-time-reject or fold an
out-of-range constant) swept at idx in
{0,1,31,32,33,40,63,64,65,127,4095,65535} uniform-per-case, plus two
per-lane-VARYING index cases (`idx=lane+32`, `idx=lane` identity control);
`shuffle_xor_dyn` (mask in {0,1,31,32,33,63}); `quad_shuffle_dyn` (idx in
{0,1,2,3,4,5,8,255}). Every case's raw 32-lane output vector is recorded
(gated) even where no single-value oracle is asserted, so the RESULTS
analysis can fit a model post hoc against the full swept table.
**Coverage: COVERED.**

**SIMD-04 — Are inclusive/exclusive scans and reductions correct for partially
active and divergent subgroups?**
Hypothesis: yes for the specific "some lanes execute the scan under an `if`,
others skip it entirely" divergence shape (a real per-lane predicate derived
from `thread_position_in_grid` parity, not a uniform branch) -- active lanes
should see a scan restricted to the active subset in lane order, inactive
lanes see whatever the `else` arm computes (not the scan). Refuter: an active
lane's scan value including a contribution from an inactive lane (would
indicate an inactive lane silently contributes 0/garbage into the reduction
tree rather than being fully excluded), or any active-lane value not matching
the closed-form active-only-prefix formula. Plan: `scan_divergent` -- odd
lanes take the `else` arm (sentinel -1, no scan call at all); even lanes call
`simd_prefix_exclusive_sum(1)`, `simd_prefix_inclusive_sum(1)`, `simd_sum(1)`.
Host oracle = active-lane-order prefix count. **Coverage: COVERED.**

**SIMD-05 — Are quad lane numbering and horizontal/vertical/diagonal neighbor
mappings completely known?**
Hypothesis: prior work (EXP-0018) established only the LINEAR mapping
(`thread_index_in_quadgroup = lane % 4`); the 2-D geometric mapping (which xor
mask is horizontal/vertical/diagonal, and the within-quad linear lane order
used by `quad_shuffle_up/down`'s "fill" boundary behavior) is UNTESTED. Two
independent probes: (a) compute-side linear semantics (`quad_xor_map`,
grid=32/tg=32, host oracle assuming 4-consecutive-lane quads); (b)
fragment-side GEOMETRIC semantics -- each fragment encodes its own integer
pixel coordinate, reports its quad-partner's coordinate via
`quad_shuffle_xor(code,{1,2,3})`/`quad_shuffle_up/down(code,1)`, and the true
screen-space neighbor at each mask is compared against `(x^1,y)`/`(x,y^1)`/
`(x^1,y^1)`. Refuter: any pixel's reported partner not matching its true
geometric neighbor under a FIXED single hypothesis (i.e. the mapping is not
simply "xor-mask flips the corresponding coordinate bit"). Plan: 4x4 render
target (`tools/shdump --render` + `tools/agxtest agxrender`, both read-only,
pixel-color readback only -- no new binary tooling), one fragment function
per mask/direction, `f_quad_selfcode` as the coordinate-encoding round-trip
sanity baseline. **Coverage: COVERED** (both the linear compute half and the
2-D geometric fragment half).

**SIMD-06 — Does a SIMD-group barrier compile to no instruction because all 32
lanes execute in lockstep with the required memory visibility?**
Hypothesis: `simdgroup_barrier` (distinct from `threadgroup_barrier`, which
EXP-0093 already showed DOES emit a real `0x07`-family instruction for every
memory class including `mem_none`) compiles to LITERALLY ZERO added
instructions for at least `mem_none`, since a true single simdgroup already
executes in lockstep and needs no synchronization instruction; `mem_device`/
`mem_threadgroup` are less certain (they might still need a fence op even
within one simdgroup, mirroring `threadgroup_barrier`'s device-fence case).
Refuter: any `simdgroup_barrier` variant that changes `_agc.main`'s compiled
bytes at all (structural), OR a convergence-requiring correctness kernel that
fails WITH the barrier present (would show the "no instruction" reading is
wrong, not just incomplete). Plan: (1) `structural_group` compile-only byte
comparison across `sgbar_none`/`sgbar_memnone`/`sgbar_memtg`/`sgbar_memdev`
(4 compiles, 0 GPU risk); (2) a correctness run of each variant (`a*2`,
non-cross-lane, sanity only); (3) `sgbar_conv`/`sgbar_conv_none` -- a
per-lane-variable-delay + cross-lane DEVICE-memory read convergence litmus
(device buffer used instead of `[[threadgroup(0)]]` because the read-only
`agxrun.m` testbed does not expose `setThreadgroupMemoryLength:` -- Note-A),
mirroring EXP-0093's `tgdiv2`/`tgdiv_dev` design but using
`simdgroup_barrier(mem_device)` in place of `threadgroup_barrier`, at
tg=32=simd-width so "simdgroup" and "threadgroup" scope coincide.
**Coverage: COVERED.**

**SIMD-07 — Are helper lanes included or excluded correctly by every subgroup
and quad operation exposed to fragment shaders?**
Hypothesis: EXP-0091 already HW-validated that a data-MOVEMENT op
(`quad_shuffle_xor`) successfully reads a just-demoted (discarded) lane's own
live register -- i.e. data ops INCLUDE helper lanes. The genuinely open half
is whether VOTE/BALLOT-class ops (`simd_active_threads_mask`, and by
extension `simd_ballot`) EXCLUDE a demoted lane the way a naive "helper lanes
don't count as truly active" model would predict. Refuter: if a surviving
lane's observed `popcount(simd_active_threads_mask())` does NOT change after
a neighbor discards, that DIRECTLY REFUTES the exclusion hypothesis (a
genuinely surprising, first-class negative result to report honestly, not to
suppress). Plan: `f_ballot_baseline` vs `f_ballot_onediscard` (fixed pixel
(0,0) discards) on a 4x4 target, popcount encoded in the red channel;
`f_ballot_baseline_raw`/`f_ballot_onediscard_raw` report the RAW low-16 mask
bits (not just popcount) in R+G to distinguish "the specific lane's bit
changed" from "some other bit changed" if popcount alone is ambiguous.
**Coverage: COVERED**, with an explicit note that this experiment tests only
`simd_active_threads_mask()` as the vote-class representative (not the full
`simd_ballot`/`simd_all`/`simd_any` family under discard) -- flagged as a
narrower-than-ideal but real, HW-validated probe, not silently generalized
beyond what was tested.

## Confounders / limitations acknowledged up front

- **Compiler discretion.** Every kernel is compiled by Metal's own MSL→AGX
  compiler (`newLibraryWithSource:`), not an independently-authored assembler
  for these instruction families. Where a kernel's own hand-authored MSL
  shape happens to compile to full predication (no branch at all — the
  `predalias` baseline is exactly this, and is reported as a NEGATIVE finding,
  not discarded), that bounds what triggers real branch machinery but is not
  itself proof the compiler could not, in principle, choose differently.
- **`icmp_pred`'s `dst_pred` census is compiler-habit evidence, not exhaustive
  proof of the field's semantics** beyond the specific splice values tested
  (0x1, 0x5, 0xf against a natural 0x0). Values outside this set are UNTESTED.
- **Branch-reach splice deltas are chosen, not exhaustive** — six points
  (±8B/±4096B/±0x400000B) bound the practical range qualitatively; they do not
  establish the EXACT byte where behavior transitions.
- **SIMD-07 tests only `simd_active_threads_mask()`**, not the full vote
  family, under exactly one discard shape (single fixed pixel, 4x4 target).
- **Fragment-stage SIMD width (part of SIMD-01) is DEFERRED**, not run as a
  dedicated sweep in this experiment (see SIMD-01 above).
- All results are M4/G16G only; no A18 Pro claim is made anywhere.
