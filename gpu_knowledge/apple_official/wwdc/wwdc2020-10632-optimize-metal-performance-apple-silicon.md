# Optimize Metal Performance for Apple Silicon Macs

Source: https://developer.apple.com/videos/play/wwdc2020/10632/

## Session Description

Apple silicon Macs are a transformative new platform for graphics-intensive apps. Demonstrates
how to leverage the GPU to create blazingly fast apps and games. Covers TBDR GPU architecture,
workload scheduling, rendering pipeline structure, and shader optimizations for the Apple GPU
shader core.

---

## 1. Apple GPU Architecture Overview

### Tile-Based Deferred Rendering (TBDR)
- Apple-designed GPUs use TBDR architecture for high performance and low power
- Uses high bandwidth, low latency tile memory to eliminate overdraw and reduce system memory
  traffic
- Processing pipeline:
  1. Vertex stage: Transforms and bins geometry into screen-aligned tiled vertex buffers
  2. Fragment stage: Processes entire tiled vertex buffer on-chip using fast tile memory
  3. GPU rasterizes all primitives in a tile before shading any pixels

### Load and Store Actions
- Make explicit how render pass attachments move in and out of tile memory
- Critical for minimizing system memory bandwidth

## 2. Workload Scheduling Optimization

### Challenge: Creating Unnecessary Dependencies

Apple GPUs execute vertex, fragment, and compute workloads in parallel using independent
hardware channels. Overlapping maximizes GPU utilization.

**Problem Pattern:**
```
Render Pass 0 (Fragment) -> writes data
      (unnecessary dependency)
Render Pass 1 (Vertex) -> reads data
```
This creates "bubbles" of inactivity in the vertex stage.

**Solution A: Separate Resources**
```swift
// Bad: Same resource creates false dependency
renderPass0WritesTo(sameResource)
renderPass1ReadsFrom(sameResource)  // Creates dependency

// Good: Separate resources
renderPass0WritesTo(resource0)
renderPass1ReadsFrom(resource1)     // No dependency
```

**Solution B: Use Untracked Resources**
Mark resources as untracked for explicit synchronization control.
You are responsible for inserting Metal fences or events.

**Solution C: Pass Reordering**
- Encode independent work as early as possible
- Metal automatically reorders when possible, but explicit reordering is better

Tools: Use Metal System Trace to identify missed overlap opportunities (shows vertex,
fragment, and compute stage overlaps visually).

## 3. Minimizing System Memory Bandwidth

Load and store actions for render pass attachments consume the majority of system bandwidth.
Key optimization: Reduce number of render passes.

### Issue 1: Splitting Single Logical Pass into Multiple Physical Passes

Bad: Three separate command buffers for same attachments.

Good: Use parallel render command encoder for multi-threaded encoding without execution overhead.
Metal combines sub-encoders into single render pass, saving bandwidth.

### Issue 2: Changing Load/Store Actions Creates New Passes

Merge opaque and translucent rendering into one pass by setting appropriate store actions:
```swift
renderPassDescriptor.colorAttachments[0].storeAction = .store
renderPassDescriptor.depthAttachment.storeAction = .dontCare  // Not needed
```

### Issue 3: Attachment Ping-Ponging

Use multiple render targets (up to 8 color attachments) instead of repeatedly switching
attachment sets for each light. Use memoryless textures for intermediate data:
```swift
textureDescriptor.storageMode = .memoryless
renderPassDesc.colorAttachments[1].storeAction = .dontCare
```

### Issue 4: Standalone Clear Operations

Bad: Clear in separate render pass.

Good: Fold into main pass with load action:
```swift
renderPassDescriptor.colorAttachments[0].loadAction = .clear
renderPassDescriptor.colorAttachments[0].clearColor = clearColor
```

### Issue 5: Multi-Sampled Resolve

Bad: Store MSAA data, then resolve in separate pass.

Good: Resolve as part of same pass using store action:
```swift
renderPassDesc.colorAttachments[0].resolveTexture = resolveTexture
renderPassDesc.colorAttachments[0].storeAction = .multisampleResolve
```
Mark MSAA textures as memoryless.

## 4. Hidden Surface Removal (HSR) Optimization

### Fragment Categories

**Opaque Fragments**
- Always occlude everything beneath them
- HSR can reject all pixels beneath them before shading
- Most efficient for HSR

**Feedback Fragments**
- Generated by fragment functions with `discard` or custom depth
- Alpha-tested foliage

**Translucent Fragments**
- Blend with background
- Least efficient for HSR

### Optimal Draw Order

1. Opaque geometry (any order, usually by material)
2. Feedback fragments (order matters for correctness)
3. Translucent objects (back-to-front)

### HSR Efficiency Issues

**Issue 1: Resource Writes from Fragment Functions**

Problem: Metal must execute all fragments even if occluded when fragment writes to memory.

Solution: Use `early_fragment_tests` attribute:
```metal
fragment void renderFragment(
    [[early_fragment_tests]] const device Data &data [[buffer(0)]]) {
    if (depth_fails_test) return;  // Safe to reject early
    data_output[atomicAddition...] = value;
}
```

**Issue 2: Write Masking**
Restricts channels written - reduces HSR efficiency.

**Issue 3: Partial Attachment Writes**
Fragment function must write ALL attachments; unwritten attachments become unintentional
write masking. Initialize unused output data to zero.

### Depth Pre-pass on Apple GPUs

Traditional: Two passes (depth only, then color).

Apple GPU Alternative:
- HSR automatically rejects hidden fragments
- Geometry processed only once
- No depth attachment storage needed
- No z-fighting artifacts
- Depth pre-pass is usually counterproductive on Apple GPUs.

## 5. Advanced TBDR: Tile Shaders for Deferred Shading

### Traditional Deferred Pipeline
```
Pass 1: Render G-Buffer (albedo, normals, roughness)
      (store to system memory)
Pass 2: Lighting pass using G-Buffer
      (load from system memory)
```

### Optimized: Programmable Blending

Access current pixel values from all color attachments directly from tile memory.
No system memory roundtrip:
```metal
fragment float4 lightingShader(
    float4 albedoValue [[color(0)]],
    float4 normalValue [[color(1)]],
    float4 roughnessValue [[color(2)]]) {
    float3 lighting = computeLighting(albedoValue, normalValue);
    return float4(lighting, 1.0);
}
```

Note: Depth not directly accessible in tile memory. Workaround: Store depth in dedicated
color attachment.

### Tile-Based Compute Dispatches

Use tile shaders to perform light culling mid-render-pass:
```swift
let renderPassDesc = MTLRenderPassDescriptor()
renderPassDesc.tileWidth = 32
renderPassDesc.tileHeight = 32
renderPassDesc.threadgroupMemoryLength = MemoryLayout<LightInfo>.size * 8

// G-Buffer attachments as memoryless
renderPassDesc.colorAttachments[0].storeAction = .dontCare  // albedo
renderPassDesc.colorAttachments[1].storeAction = .dontCare  // normals
renderPassDesc.colorAttachments[2].storeAction = .dontCare  // roughness
renderPassDesc.colorAttachments[3].storeAction = .store      // final lighting

// Within single render encoder:
// 1. G-Buffer generation draw
// 2. Tile dispatch for light culling (implicit barrier)
// 3. Lighting draw (reads per-tile light list from threadgroup memory)
```

Benefits:
- Entire pipeline in single render pass
- G-Buffer stays in tile memory throughout
- Only final lighting stored to system memory

## 6. Apple Shader Core Optimization

### Architecture Overview
- Modern scalar architecture aligned with Metal Shading Language
- Prefers loading/storing vector types directly
- Contains 16-bit and 32-bit ALUs
- Can hoist constant code execution and prefetch constant data

### Address Spaces

**Device Address Space:**
- Read-write memory, virtually no size restrictions
- Use when: Unknown data amount per thread, each thread reads different items, limited reuse

**Constant Address Space:**
- Read-only, limited capacity
- Optimized for data constant across all threads in same draw/dispatch
- Use when: Fixed size, same item reused many times

Decision tree:
```
Is amount of data unknown at compile time, or each thread reads different number of items?
  YES -> use device address space
  NO  -> How many times is each item read?
           Few times -> use device address space
           Many times -> use constant address space
```

### Data Types and ALU Optimization

Apple GPUs are optimized for 16-bit data types.

Benefits of 16-bit over 32-bit:
- Fewer registers allocated -> higher shader core occupancy
- Faster arithmetic instructions
- Better ALU utilization
- Type conversions are free

Use half-precision literals explicitly:
```metal
// Bad: Literals force promotion to 32-bit
half result = a + b - 2 + 5;   // Whole expression becomes float

// Good: Use explicit half literals
half result = a + b - 2h + 5h; // Stays in half precision
```

### Memory Access Optimization

**Issue 1: Stack-Allocated Arrays with Dynamic Indices**

```metal
// Bad: Dynamic indexing of stack array -> compiler cannot eliminate spilling
float compute_value(uint index) {
    float values[3] = {1.0, 2.0, 3.0};
    return values[index];
}

// Good: Compile-time known indices -> compiler optimizes
float compute_value() {
    float values[3] = {1.0, 2.0, 3.0};
    return values[0];
}
```

Detection: Use GPU Frame Debugger in Xcode -> Pipeline Statistics -> remarks panel.

**Issue 2: Unsigned Index Wrapping**

```metal
// Bad: Unsigned types require wrapping semantic support, prevents vectorization
for (uint i = start; i < end; ++i) { buffer[i] = value; }

// Good: Signed types have undefined overflow behavior, compiler can vectorize
for (int i = start; i < end; ++i) { buffer[i] = value; }
```

**Issue 3: Non-Adjacent Struct Fields**

```metal
// Bad: Non-adjacent fields prevent vectorization
struct Foo { float A; float B; float C; };
float sum = foo.A + foo.C;  // Can't load A and C together

// Good: Adjacent fields or vector type
struct Foo { float2 AC; float B; };
// OR reorder: float A; float C; float B;
```

## Summary of Key Takeaways

1. Workload Scheduling: Eliminate unnecessary data dependencies to maximize vertex-fragment-compute overlap
2. Bandwidth Minimization: Reduce render passes, merge adjacent passes, use memoryless textures
3. Hidden Surface Removal: Proper draw ordering (opaque -> feedback -> translucent), avoid partial writes
4. Tile Shaders: Keep intermediate data in tile memory using programmable blending and tile dispatches
5. Shader Optimization: Use 16-bit types, correct address spaces, avoid stack arrays and unsigned wrapping
6. Tools: Metal System Trace for profiling, GPU Frame Debugger in Xcode for detailed analysis
7. No Depth Pre-pass Needed: HSR handles visibility automatically on Apple GPUs
