## Overview

This post documents the development of an open-source shader compiler for Apple's M1 GPU (AGX). Within the first week of compiler development, basic vertex and fragment shaders were compilable, sufficient to render 3D scenes. The compiler is integrated into Mesa and uses the NIR intermediate representation.

---

## Compiler Architecture

The compiler pipeline follows a standard SSA-based design:

```
GLSL/SPIR-V Input
      ↓
    NIR (New Intermediate Representation) — Mesa standard IR
      ↓
  Custom AGX SSA-based IR
      ↓
  Instruction Combining / Optimization Passes
      ↓
  Scheduling (minimize register pressure)
      ↓
  Register Allocation (with SSA elimination)
      ↓
  Post-allocation Scheduling (instruction-level parallelism)
      ↓
  Binary Instruction Packing
      ↓
  AGX Machine Code Output
```

### Why NIR instead of LLVM?

The author chose Mesa's **NIR** (New Intermediate Representation) rather than LLVM as the input IR. Reasons:

- NIR is already used by other Mesa GPU drivers (Intel, AMD via RadeonSI/RADV, Panfrost, etc.)
- NIR has GPU-specific lowering passes already written (blending, vertex attribute fetch emulation, etc.)
- Lower overhead than LLVM for GPU shader compilation
- Valve rewrote AMD's GPU compiler to use NIR for similar reasons

## AGX GPU Hardware Characteristics

### Register File

- **Register count per thread:** 256 half-word (16-bit) registers
- **Register file size per threadgroup:** ~208 KiB
- **Concurrent threadgroups:** 24
- **Total GPU register file size:** ~4.875 MiB (24 × 208 KiB)

### Thread Occupancy vs. Register Usage

The relationship between register usage and maximum concurrent threads is non-linear. Reverse-engineered occupancy table:

| Register Usage (16-bit regs) | Maximum Threads |
|------------------------------|-----------------|
| ≤104                         | 1024            |
| 112                          | 896             |
| 120–128                      | 832             |
| 136                          | 768             |
| 144                          | 704             |
| 152–160                      | 640             |
| 168–184                      | 576             |
| 192–208                      | 512             |
| 216–232                      | 448             |
| 240–256                      | 384             |

**Occupancy decrease rate:** Approximately 64 threads lost per ~8 additional registers used beyond 104.

This non-linear relationship is typical of GPU architectures where register file space is a finite shared resource.

### Data Type Support

- **16-bit (half precision):** Native support, primary precision for many operations
- **32-bit (single precision):** Native support
- **Free conversions:** 16-bit ↔ 32-bit conversions on both source and destination operands incur no additional cost (they are encoded as modifiers in the instruction word)
- **Scalar architecture:** All operations are scalar; vectors are handled by the compiler unrolling to multiple scalar operations

### Superscalar Execution

The hardware is superscalar with more 16-bit execution units than 32-bit. The compiler can exploit this for instruction-level parallelism.

---

## Notable Hardware Absences: Fixed-Function Hardware

Unlike traditional GPU designs, the AGX GPU **lacks fixed-function hardware** for:

1. **Vertex attribute fetch** — Reading vertex buffer data and converting it to shader input types
2. **Uniform buffer object (UBO) reads** — Accessing uniform/constant data

These operations are instead implemented through **shader code** generated by the compiler. This reflects Metal's compute-centric design philosophy where most functionality is expressed as shader programs.

**Implication for the driver:** The compiler must generate extra code to fetch vertex attributes and uniforms as part of each shader, rather than relying on hardware to do it automatically.

## Development Status at Time of Post

### Working Features

- Compiles vertex and fragment shaders from GLSL (via NIR)
- Most OpenGL ES 2.0 arithmetic operations
- Basic optimization passes
- Instruction packing (multiple operations per instruction word where applicable)

### Pending Features

- Control flow (if/else, loops)
- Texture sampling instructions
- Advanced scheduling
- Full conformance
